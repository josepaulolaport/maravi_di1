# API layer

The shapes in `contract/` are the adopted HTTP contract (OQ-26 item 8), frozen at 57b4df0 (Lead Backend, 2026-10-19); `docs/interfaces.md` records them. The proposals below are kept as the history of each decision.

- `contract/`: response and request types. snake_case names follow `docs/schema.sql`; decimals are strings; `null` means unavailable.
- `http.ts`: the only HTTP client. JSON in and out; RFC 9457 problem+json errors become `ApiError` (OQ-15).
- `endpoints.ts`: one typed function per endpoint. Feature hooks call these.
- `mocks/`: the MSW fake backend: a stateful in-memory store (`db.ts`) seeded from one coherent scenario (`fixtures.ts`), with the documented validations, one status per date and chain (`processing.date_status`, OQ-23), and a run that advances one step per poll: dispatch, then one date per poll. Its "today" is the app's clock (São Paulo); the tests pin that clock to `MOCK_TODAY`.
  - A run publishes each date as it commits it: the scenario's precomputed results, that chain's Pendências for the date replaced (OQ-26), and the date's status. The fake does not calculate: a date on or after a write since the seed fails, so the run ends **Falhou** with a "Backend simulado" message there, and the dates before it stay published.

At Wave 5 the hand-written types are replaced by types generated from the backend's OpenAPI (`npm run gen:api`).

## OQ-21 to OQ-31: two chains, one status per date, per-date publication

Recorded by lane X (OQ-21, OQ-22; OQ-23 to OQ-26 in PR #43). The user ruled that these shapes are the HTTP contract, with the corrections agreed with lane X (OQ-26 item 8):

- `ProcessingScope = CASH | POSITIONS | ALL`: required on `POST /processing/requests` and on the preview; echoed on every `ProcessingRequest`.
- `ProcessingPreview.predecessor = {cash, positions}`, replacing `predecessor_state`: start−1's chain status, or `ZERO_STATE` when that chain has nothing before it (positions: no trade; cash: no entry of either type, OQ-26). There is no `VALID`.
- `PortfolioSummary = {date, cash, positions, aum}`; cash and positions each carry their own `status`, the date's chain status from `processing.date_status` (OQ-23, OQ-31): `PROCESSED` Processado, `PROCESSED_WITH_ISSUES` Processado com pendências, `RUNNING` Processando, `FAILED` Erro, `NOT_PROCESSED` Não processado; `published_at` is that chain's processing time, shown as "Processado em dd/mm/aaaa hh:mm". The cash also carries its day's components: `trades_cash_flow`, `deposits` and `withdrawals` (user, 2026-10-18).
  - `cash.balance` comes from `portfolio.cash_balances`;
  - `positions` holds the market value, the valuation status and the P&L;
  - `aum` is just the value, `null` when either side is missing. It has no status (user, 2026-10-19): the two badges already tell the state of its sides.
- One status everywhere (user, 2026-10-18): `PortfolioPositions` is `{date, status, published_at, items}`, and each `PnlPoint` has `status` and `published_at`, both for the positions chain. This replaces P9's `publication` + `stale`. Each `PnlPoint` also carries `range_cumulative_pnl`, the backend's sum of daily P&L from the requested start date, `null` from the first gap; the chart draws it and never sums (OQ-31).
- OQ-31 (replaces OQ-22 and the staleness of OQ-23 item 3): there is no staleness. A write changes no status; processed figures stay until the date is processed again. A run needs, per chain in scope, the day before each date processed (`PROCESSED` or `PROCESSED_WITH_ISSUES`, a failed day counting as not processed) or the chain's zero state; otherwise that date and chain read `FAILED`, the run ends `FAILED` with `CASH_PREDECESSOR_MISSING` or `POSITIONS_PREDECESSOR_MISSING` (positions when both) and "Dia anterior não processado", and the preview warns. Pendências has two types: `MISSING_REFERENCE_PRICE` and `EXPIRED_OPEN_POSITION`; `STALE_PREDECESSOR` and `Issue.chain` are dropped.
- OQ-30: cancel-and-replace is removed (cancel, then request again). A position row's `reference_pu`, `reference_rate` and `reference_source` are the current preferred price in the price table (PU 0 after maturity), so a price recorded after processing shows on the row before the date is reprocessed.
- A run (OQ-23): `ProcessingRequest = {id, scope, start_date, end_date, status, progress_date, error_code, error_message, created_at, updated_at, dispatched_at, started_at, finished_at, cancel_requested_at}`, eight statuses (no `SUPERSEDED`). Each date is published on its own: `progress_date` is the last one committed; days done and the date being processed derive from it. A failure at a date marks it `FAILED` and ends the run; a cancel lets the current date commit, and a cancel during the last date ends `COMPLETED` (or `COMPLETED_WITH_ISSUES`, OQ-26 item 9). A run ends `COMPLETED_WITH_ISSUES` when a date it wrote is `PROCESSED_WITH_ISSUES`. "Solicitar novo processamento" prefills from the failed date, or the first date not reached, to the original end.

## OQ-32 to OQ-40

Recorded by lane X in PR #54; the mock follows them.

- OQ-32: a ledger deletion is permanent. An unknown or already-deleted id is 404 and deletes nothing; a repeated id counts once; an empty `ids` is 422 on `ids`.
- OQ-33: a contract code is trimmed and upper-cased; an unknown id in a body is 422 on that field (404 only for a path id); `search` ignores case and accents; `Instrument.last_reference` is always `null` for now, shown as "—".
- OQ-35: Portfolio reads after today are 422 `FUTURE_DATE`: on `date` for the summary and the positions, on `end_date` only for the P&L series (a later `start_date` is `INVALID_RANGE`).
- OQ-37: `GET /processing/issues` is deduplicated on read: a missing price once per (asset, `required_price_date`), an expired open position once per asset, each with its earliest `affected_date`. The Pendências table shows the needed price date ("—" for an expired position) and, under "Afetado desde", the row's earliest affected date.
- OQ-39: `GET /processing/preview` returns `predecessor.cash` and `predecessor.positions` for every scope; the screen shows and warns only for the scope's chains.
- OQ-38, OQ-40 items 2 and 5: a chain written on a date stores that date's AUM as cash + market value only when the other chain is `PROCESSED` or `PROCESSED_WITH_ISSUES` there, whichever run wrote it; otherwise `null`. A chain is in its zero state on D only when no date before D has any status for it and no entry of its type is dated on or before D−1, so a gap after an earlier status fails D.
- OQ-36, OQ-40 items 3 and 6: on an ALL run, a chain that fails on D (its predecessor, or the fake's changed inputs) reads Erro there and stops; the other chain is still written on D and goes on to the end. The run ends `COMPLETED_WITH_ISSUES` with the first failure's `error_code` and `error_message`, `CANCELLED` keeping them when cancelled, and `FAILED` only when both chains fail. `ProcessingRequest` gains `failed_date` and `failed_chain` (`CASH` or `POSITIONS`, positions when both fail at once, the run's chain on a single-chain run, `null` for a failure outside every chain or a run that never failed).
