# Maravi DI1 Backoffice — Database schema specification

**Status:** implemented. [`schema.sql`](schema.sql) is the complete PostgreSQL 16 schema (17 tables) and the result of Alembic revisions 0001 to 0007 (head `0007`); `tests/integration/test_migrations_match_schema.py` checks that the revisions build the same columns, constraints and indexes, and `test_cash_chain_migration.py`, `test_one_status_per_date_migration.py`, `test_no_reference_copy_migration.py`, `test_no_staleness_migration.py`, `test_hard_delete_migration.py`, `test_failed_chain_migration.py` and `test_cash_description_migration.py` cover the CHECKs and keys added by 0002 (OQ-21, OQ-22), 0003 (OQ-23, OQ-24, OQ-25), 0004 (OQ-30, OQ-31), 0005 (OQ-32), 0006 (OQ-40) and 0007 (OQ-51). Last verified on 2026-10-19: upgrade to head on a fresh PostgreSQL 16 and the full backend suite pass. The column order of a migrated database differs from this file (PostgreSQL appends added columns), so nothing may rely on positional column order. A schema change needs a recorded decision and a new revision; released revisions are never edited. **OQ-50 (2026-10-19) changes no DDL in this document:** it stops writing `portfolio_metrics.aum`, `date_status.portfolio_previous`/`cash_previous` and the `RUNNING` date status, and removes the use of `platform.inbox_messages`; they stay in the schema unused, with no migration (a consequence of the user excluding A9, the migration squash; as OQ-47 item 1), unless the implementing PRs on `simplify` record one.

## Settled scope

- Exactly **one portfolio**, so no `portfolio_id` or persistent `portfolio` business entity.
- Seven code modules: `asset`, `ledger`, `pricing`, `prices`, `portfolio`, `pnl`, `processing`. Database schemas only where tables exist; `pricing` and `pnl` are calculation-oriented.
- Calendar-day accounting and P&L processing; DI1 simplified **DC/365** calculation. No automatic weekend/holiday price carry-forward. Price lookup is **exact date**.
- `prices` owns reference observations from `MANUAL` and `B3`; `MANUAL` takes precedence, then `B3`. Each source has at most one observation per asset and date; a later set of the same key deletes the current row and inserts the new one, and a removal deletes it (OQ-25, OQ-26).
- `ledger` alone owns execution prices, in immutable entries: one table, `ledger.entries`, holds trades and cash movements (OQ-24). Prices do not flow from trades into reference prices.
- `portfolio.positions` stores signed quantities. `portfolio.position_metrics` stores open-position average entry PU/rate, signed position market value (`financial_total`), and asset P&L components. `portfolio.portfolio_metrics` stores signed positions' total market value, AUM, portfolio P&L and completeness. `portfolio.cash_balances` stores the cash chain: each day's balance, trades cash flow, deposits and withdrawals (OQ-21).
- **AUM = cash_balances.cash_balance + portfolio_metrics.positions_market_value** for the same date, under the agreed simplified accounting model; no gross/net exposure fields and no duplicate `total_equity` column. Cash and positions are two separately processable chains (OQ-21). Since OQ-50 item 1 it is computed at read time, not stored.
- Only user-requested date-range processing enqueues work. An input change saves only its fact: it marks nothing and **never automatically enqueues P&L calculations**; a date's results change only when the user processes it again (OQ-23, OQ-31).
- Multiple overlapping requests can be queued. Exactly one `RUNNING` job globally, because one worker takes and runs them one at a time (OQ-45, OQ-46). Cancellation is cooperative. A run publishes each date in its own transaction; there is no staging, no revision check and no `SUPERSEDED` (OQ-23).
- PostgreSQL is the authoritative durable job queue. RabbitMQ transports work commands. `platform.outbox_messages` and `platform.inbox_messages` support at-least-once reliable delivery and consumer deduplication. Since OQ-50 item 2: one outbox message per request (its `request_id`) plus a periodic sweep in the worker; no inbox deduplication.

## Important database integrity decisions

1. Cross-schema foreign keys **are allowed**. They protect persisted IDs but do not authorize writing another module's tables through another module's services.
2. Instrument/product codes are unique case-insensitively; instrument codes and trade values are validated.
3. Ledger entries are never edited: repository methods must not permit economic modification. A delete is a hard `DELETE`, all or nothing for a multi-delete, with no reason and no audit trail of the deleted rows (OQ-24, OQ-32). This is **not** DB-enforced immutability against privileged direct SQL writes.
4. `reference_prices` has one row per `(asset_id, reference_date, source)`, without revisions: a later set of the same key deletes the current row and inserts the new one (new id); a removal deletes it (OQ-25, OQ-26). Active source selection is a domain/read rule (`MANUAL > B3`) and does not delete lower-priority source observations.
5. `position_metrics` stores no reference price: the reference PU, rate and source of a date are read from `prices.reference_prices` (current preferred: MANUAL, else B3, exact date). A published day keeps its computed `financial_total` and P&L, so after a price change the screen shows the current price next to the last processed figures until the user processes the date again (OQ-30, OQ-31).
6. The tables use PostgreSQL `NUMERIC` to preserve Python `Decimal` financial arithmetic. Precision (OQ-3): 34-digit context, `ROUND_HALF_UP`; calculated PU stored with 10 dp and calculated rate with 12 dp; typed values with more decimals are rejected; money stored exact and rounded to 2 dp only in the UI. Bounds are only the CHECKs below (OQ-14).
7. Missing valuation may yield `NULL` market value, daily P&L and AUM, **not zero**. Cash, quantities and average costs remain available. Zero closing quantity has zero closing market value, but same-day trades may still require a reference PU for Trades P&L.
8. `portfolio_metrics` carries both accounting-independent and price-dependent values; completeness is explicitly recorded via `valuation_status` and `pnl_status`.
9. Publication is per date (OQ-23): one transaction writes the date's rows of the run's scope — `cash_balances` (CASH); `positions`, `position_metrics`, `portfolio_metrics` (POSITIONS); all four (ALL; on an ALL run where one chain has stopped, OQ-36, only the surviving chain's tables) — sets the date's chain statuses and `*_processed_at` in `date_status` and the run's `progress_date`. There is one worker and no claim token or lease (OQ-45). Since OQ-50 item 4 the date's transaction sets no `RUNNING` status first.
10. A cancellation is checked between dates: the current date commits and later dates are not touched. A failure at D rolls D back and marks D `FAILED` for the chain; later dates are not touched (OQ-23).

## Application invariants (not adequately expressible as ordinary CHECK constraints)

- The hierarchy must ensure that `asset.futures.product_id` points to a product whose class belongs to instrument type `FUTURE`; futures instruments require a maturity date. Enforce in Asset domain and integration tests. If untrusted direct DB writers are later allowed, add a DB trigger/denormalized composite FK strategy.
- A stored reference-rate and reference-PU pair must be mathematically consistent with its face value, maturity and the 365-day convention. Official source PU is authoritative; a calculated implied rate is derived metadata. Do not synthesize an official observation from a calculator preview.
- Each portfolio day's position is obtained by chronologically applying transactions, including closes and reversals. A reversing trade may close an old position and establish a new opposite position, without splitting the immutable ledger record.
- `position_metrics.daily_pnl = position_pnl + trades_pnl` if all inputs are complete. `portfolio_metrics.daily_pnl` is the sum of **all expected** asset daily P&L values, not just available rows. No capital deposits/withdrawals enter trading P&L.
- Cash movements affect cash; under the agreed simplified model, the trade cash effect is `-signed_quantity * execution_pu`. The cash chain reads only trades and cash movements; `cash_balances` rows chain day to day (OQ-21). The multiplier is stored but not applied (OQ-2). Daily P&L is never posted into cash.
- `ledger.entries`: `entry_time` is required for both types, and order is `(entry_date, entry_time, seq)` with one `seq` shared by trades and cash (OQ-13, OQ-24). A trade's cash effect is computed on read, never stored. Nothing is dated after today (São Paulo); trades and prices may be dated up to the maturity date inclusive, never after it; on the maturity date `execution_rate` is stored as 0 (OQ-1, OQ-14). A CASH entry may carry a `description` of at most 200 characters, stored trimmed and composed (NFC) and `NULL` when blank; a TRADE never has one (CHECK `entries_description_cash_only`, OQ-51).
- After an instrument's maturity date its reference PU is 0 by definition: no `reference_prices` row exists or is accepted, and the read model shows `reference_pu = 0` with no source (OQ-30). An open position after maturity raises `EXPIRED_OPEN_POSITION` (OQ-1).
- A `positions` / `position_metrics` row exists for D exactly when the asset is expected on D: Q[D−1] ≠ 0 or a trade on D, including quantity 0 (OQ-10). `position_pnl` is 0 when Q[D−1] = 0 (OQ-4). The D−1 reference PU is D−1's current preferred price in `prices.reference_prices` (OQ-9, OQ-30).
- On a missing required reference PU, the worker produces a `processing.issues` record and incomplete results. `cumulative_pnl` remains unavailable from the first incomplete portfolio P&L day onward until the gap is resolved.
- Only a run writes `processing.date_status`: `RUNNING`, then `PROCESSED`, `PROCESSED_WITH_ISSUES` (a missing price or an expired open position) or `FAILED`, and on commit the chain's `*_processed_at`. A write in Ledger or Prices saves only its fact: no status changes and nothing is enqueued (OQ-31). Since OQ-50 item 4 a run never writes `RUNNING`: each date goes from its old status to its new one in one transaction, and reads show Processando for the active run's current date (`progress_date + 1`).
- A job processes exactly [A, B] of its scope (OQ-11, OQ-21) and may start on any date. For each date D of a chain, the worker checks that D−1 is `PROCESSED` or `PROCESSED_WITH_ISSUES` for that chain, or is the chain's zero state: no date before D has any status for the chain (`PROCESSED`, `PROCESSED_WITH_ISSUES`, `RUNNING` or `FAILED`) **and** no entry of the chain's type is dated on or before D−1 (positions: no trade; cash: no entry of either type; OQ-32, OQ-40 item 5). Otherwise D gets `FAILED`, the request ends `FAILED` with `error_code` `CASH_PREDECESSOR_MISSING` or `POSITIONS_PREDECESSOR_MISSING`, and later dates are not touched (on an ALL run where only one chain fails, that chain stops and the run ends `COMPLETED_WITH_ISSUES` with the error, `FAILED` only if both fail, OQ-36); since dates run in order, this can only happen on the run's first date (OQ-31). On an ALL run, D runs in one transaction with a SAVEPOINT per chain: a technical error rolls only the failing chain back and sets it `FAILED`, while the surviving chain's rows, `aum`, `progress_date` and statuses commit in the same transaction. A non-chain failure (outside every chain's savepoint, e.g. a lock timeout on the date's `date_status` rows; integrator choice) rolls back all of D: D is `FAILED` for every chain still alive in the run and the request ends `FAILED`; a worker crash is not a failure at D (OQ-40, OQ-45).
- Every processed day has a `portfolio_metrics` row, also with no expected asset: market value 0, position/trades/daily P&L 0, both statuses `COMPLETE`, `cumulative_pnl` carried from the previous day (`NULL` if already broken) (OQ-22). 
- `portfolio_metrics.aum` is no longer written or read since OQ-50 item 1; rows written before OQ-50 keep a stale value (dropping the column would need a migration). AUM is computed on read by `PortfolioService`: `cash_balances.cash_balance` + `positions_market_value` for the same date, or `NULL` when either is missing or either chain's `date_status` on that date is not `PROCESSED`/`PROCESSED_WITH_ISSUES` (`FAILED`, `RUNNING` or not processed), whichever run wrote it (OQ-21, OQ-38, OQ-40). An integration test checks it after CASH-only, POSITIONS-only and ALL publishes.
- A manual price takes precedence over B3 for that asset/day; when the manual row is deleted, B3 becomes the preferred source if present (OQ-25).
- A run never stops for a concurrent write, and the write marks nothing: the dates already committed keep their figures until the user processes them again (OQ-31). Recovery happens only when the single worker starts (OQ-45): the run left `RUNNING` has its `RUNNING` dates restored from `*_previous`, then resumes after `requests.progress_date` (OQ-23), or ends `CANCELLED` if `cancel_requested_at` is set; then the worker drains the `QUEUED` requests (OQ-46). Since OQ-50 item 4 there are no `RUNNING` dates to restore.
- There is no dispatcher (OQ-46). `POST /processing/requests` inserts the request `QUEUED` and, in the same transaction, one outbox message that is only a doorbell ("there is work", no request ID). On every doorbell, and at startup after recovery, the single worker repeats until nothing is `QUEUED`: one transaction row-locks the oldest `QUEUED` request by `(created_at, id)` and sets it `RUNNING` with `started_at`; then it runs it. A doorbell that finds nothing `QUEUED` does nothing; a lost one is recovered by any later doorbell or by a restart, and a duplicate is harmless. One run at a time follows from the single worker draining serially (OQ-45): no lease, no claim-token fencing, no slot. The run locks its request row, then its dates. The worker may ACK the doorbell on receipt; startup recovery covers a crash (integrator reading). **Since OQ-50 item 2:** the doorbell is replaced by one message per request carrying its `request_id`; the id is for tracing only: on any message, and on a periodic sweep, the worker takes the oldest `QUEUED` request by `(created_at, id)`, so FIFO is unchanged.
- **Unused since OQ-46, with no migration:** the `requests.status` values `DISPATCHED` and `CANCELLING` stay in `requests_status_check` (and `requests_active_idx` keeps them in its predicate) but are never set: a run goes `QUEUED` → `RUNNING`, a cancelled `QUEUED` run becomes `CANCELLED` at once, and a cancelled `RUNNING` run gets `cancel_requested_at` (integrator reading for `CANCELLING`). `requests.dispatched_at` and `calculation_state.active_request_id` stay too and are never written; `calculation_state` is not locked (integrator reading).
- `processing.requests.claim_token`, `lease_expires_at` and `attempt_count` stay in the schema but are **unused** since OQ-45 (one worker, no lease, no recovery cap; OQ-43 reversed). Nothing reads or writes them, and no migration drops them (integrator choice; it avoids a migration hours before delivery). OQ-47 item 1 confirms it: no migration squash and no column drops; these statuses and columns stay documented as unused, and the README lists them as known debt.

## API and UI implications

- `GET /portfolio/positions?date=YYYY-MM-DD` returns one combined Portfolio read model from dated position/metrics/asset data. It must surface incomplete states and each chain's status and processing time, and shows the current reference price next to the last processed figures (OQ-30, OQ-31). Since OQ-50 item 3 a row is marked when the current price of D or of D−1 (integrator reading) has a `created_at` later than D's `portfolio_processed_at`.
- `GET /portfolio/summary?date=...` uses `portfolio_metrics` and `cash_balances`; each chain's status and processing time come from `processing.date_status` (OQ-21, OQ-23, OQ-31).
- `POST /processing/requests`, `GET /processing/requests`, `GET /processing/requests/{id}` and `POST /processing/requests/{id}/cancel` expose durable processing state.
- There is no cancel-and-replace: the user cancels a job, or queues a new one, as separate actions (OQ-30). No input mutation ever queues a job.
- React/Mantine receives consolidated responses. PostgreSQL is responsible for efficient joins; application services and public interfaces remain separate for writes and calculations.

## Items intentionally not invented or silently finalized

- **Maturity settlement:** decided (OQ-1) — no automatic settlement; `settlement_method` and `settlement_description` are descriptive only.
- **Multiplier semantics:** decided (OQ-2) — stored, not applied now; a future calculator module will apply it.
- **Price input details:** `rate` can be nullable for official PU-only observations. Source-specific provider identifiers, raw data payloads, correction reasons and publication timestamps can be added when B3 ingestion is implemented.
- **Historical publication at larger scale:** one transaction per processed date (OQ-23).
- **Downgrade:** `alembic downgrade 0002` rebuilds the 0002 structure empty and carries nothing back (OQ-26 item 6); it always refuses while a job is active (`allow_data_loss` does not bypass that), and refuses while ledger entries, reference prices, requests, date statuses or published portfolio rows exist, unless `-x allow_data_loss=true` is given, and then it deletes those rows. `alembic downgrade 0001` reverts OQ-21; it refuses while a job is active, or while published cash, published portfolio metrics, any staged row, a CASH-chain issue or a CASH/POSITIONS request exists, unless `-x allow_data_loss=true` is given (offline `--sql` output skips these checks). `alembic downgrade base` drops the six schemas and is meant for fresh or throwaway databases only. It refuses while trades, cash movements, reference prices, instruments or processing requests exist, unless `-x allow_data_loss=true` is given.
- **Upgrade carry-over of 0003** (integrator choices, no real data exists yet): trades keep id and seq; cash movements keep their id, get `00:00`, new seqs after every trade and a signed amount; delete reasons and descriptions are not kept (OQ-24, OQ-26); only the current price revision stays, and published metrics keep the source of the PU they used; every published date gets its chain statuses from the old markers (`STALE` on or after the marker, `FRESH_WITH_ISSUES` for a `MISSING` valuation or P&L or an expired open position, otherwise `FRESH`); issues of runs that published nothing, and issues of a date that a later published run covered for the issue's chain (chainless issue types count as positions), are deleted (OQ-26 item 5); a `SUPERSEDED` request becomes `FAILED` with `error_code = 'SUPERSEDED'`, and old cancelled or failed runs, which published nothing, lose their `progress_date`.
- **Upgrade carry-over of 0004** (integrator choices): `position_metrics` loses its reference PU and source (OQ-30); `FRESH` becomes `PROCESSED`; `FRESH_WITH_ISSUES` becomes `PROCESSED_WITH_ISSUES` (cash: `PROCESSED`, the cash chain raises no issues); a chain that carried a `STALE_PREDECESSOR` issue becomes `FAILED`; a `STALE` chain without a published row (it could only come from `FAILED`) becomes `FAILED`; any other `STALE` chain keeps its figures and becomes `PROCESSED_WITH_ISSUES` when its published positions have a `MISSING` valuation or P&L or an expired open position, otherwise `PROCESSED`; the same mapping applies to `*_previous`; `*_processed_at` is backfilled, for chains with a status, from the published row's `updated_at` (for positions an approximation: a CASH run also rewrites `portfolio_metrics` for the AUM); `STALE_PREDECESSOR` issues and `issues.chain` are dropped (OQ-31). `alembic downgrade 0003` restores the old names (`PROCESSED*` → `FRESH*`) and brings the dropped columns back empty.
- **Upgrade carry-over of 0005:** soft-deleted ledger entries are physically deleted, and `deleted_at`, `deletion_batch_id` and their CHECK go (OQ-32). `alembic downgrade 0004` brings the columns back empty; deleted entries are not rebuilt.
- **0006** (OQ-40): `processing.requests` gains `failed_date` and `failed_chain`, the run's first failure. A chain failure sets both. A failure of no chain (outside every chain's savepoint) sets only `failed_date`. A run that never failed keeps both `NULL`. "Solicitar novo processamento" on `COMPLETED_WITH_ISSUES`, or on a `CANCELLED` ALL run (OQ-40 item 6; the columns are kept on cancel), is prefilled from them. Existing runs get `NULL`. `alembic downgrade 0005` drops them.
- **0007** (OQ-51): `ledger.entries` gains `description VARCHAR(200)`, nullable, and the CHECK `entries_description_cash_only` (`type = 'CASH' OR description IS NULL`). Existing entries get `NULL`. `alembic downgrade 0006` drops the column and its descriptions.
- **Physical DB verification:** the DDL applies on PostgreSQL 16 (see Status); it still needs Alembic migration generation and comprehensive constraint/integration tests before treating it as production-ready.
