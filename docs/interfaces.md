# Maravi DI1 — Module contracts and execution boundaries

**Status:** Implementation target. Consistent with `schema.md` (2026-10-18). This document specifies service ownership and call semantics, not actual Python implementations.

## Scope and structural rules

Single portfolio (no `portfolio_id`). Modular monolith: `asset`, `ledger`, `pricing`, `prices`, `portfolio`, `pnl`, `processing`. HTTP/API service methods may be async; calculation engines are deterministic synchronous pure Python. `platform` owns database session/UoW, RabbitMQ/outbox/inbox, tracing. Cross-module access only through `public.py` contracts. No service imports another module's repositories/ORM. `Depends` only in FastAPI adapters/dependency providers. SQL lives in `infrastructure/persistence/queries`. A business mutation saves only the fact, in one Unit of Work; there is no financial-result invalidation (OQ-31).

## Contract catalog

### Asset
- `AssetReader.get_instrument(instrument_id) -> InstrumentDescriptor`
- `AssetReader.get_instruments(ids) -> Mapping[id, InstrumentDescriptor]`
- `AssetService.create_product(request)`, `create_instrument(request)`, `get_instrument(...)`, `list_instruments(...)`
- `InstrumentDescriptor`: id, code, product_id, instrument_type, asset_class, maturity_date, face_value, multiplier, settlement_method.
- Asset normalises `code` (trim + upper-case) before validating and storing it; uniqueness is case-insensitive (OQ-33).
- Asset validates product/class/type hierarchy and maturity requirements. Futures' shared specs in `asset.futures`, contract maturity in `asset.instruments`.

### Pricing
- `PricingService.calculate(instrument_id, reference_date, quote: Quote) -> Price`: the service reads the instrument through `asset.public.AssetReader.get_instrument` and builds the calculator's terms from it, so no caller passes a stale face value (lane B's approved contract request).
- `Quote` is what was typed, the single authoritative input: a rate or a PU. `Price` is the complete pair: PU, rate and input_kind, neither optional. The only convention is DC/365 (spec §4.1).
- `DI1Calculator` is pure and returns a value. Calculators never publish messages or persist results. `PriceService` and `LedgerService` can both call Pricing's public interface; P&L does **not** belong here.

### Ledger
One table, `ledger.entries` (OQ-24): each entry is a TRADE or a CASH movement, with `entry_date`, `entry_time` (required, São Paulo local time) and one `seq` shared by both types. The order is `(entry_date, entry_time, seq)` across both types. A CASH entry stores a signed `cash_amount` (positive aporte, negative retirada, never 0); a trade's cash effect is not stored, it is computed on read as −`signed_quantity` × `execution_pu` by the single function in the portfolio cash domain.
- `LedgerService.create_entry(request, *, uow) -> LedgerEntry` (a trade or a cash movement)
- `LedgerService.delete_entries(ids, *, uow) -> None`: a hard delete (OQ-32), a real `DELETE` from `ledger.entries` of one or many entries of either type, with no reason, in one transaction, all or nothing. If any id is unknown (or already deleted, which is the same thing), it raises the not-found error (HTTP 404 `NOT_FOUND`) and nothing is deleted. An empty `ids` is a validation error (422 on `ids`); a repeated id counts once (OQ-32 item 5). There is no audit trail: a deleted entry no longer exists anywhere, and processed results keep their figures until the user processes the dates again (OQ-31).
- `LedgerService.list_entries(start_date, end_date, search, order, limit, cursor) -> page of LedgerEntry`, the read behind `GET /ledger/entries` (keyset pagination on `(entry_date, entry_time, seq)`, OQ-26; method name integrator-defined).
- `LedgerReader.get_trades(start_date, end_date) -> ordered list[TradeRecord]` and `LedgerReader.get_cash_movements(start_date, end_date) -> ordered list[CashMovementRecord]` keep their names and read the entries of `ledger.entries` of their type (every row is a live entry; there is no deleted state to filter, OQ-32), in `(entry_date, entry_time, seq)` order. `CashMovementRecord` gains the time, the `seq` and the signed amount (OQ-24).
- Writes validate Asset and use Pricing when a trade is rate-only or PU-only. Validation (OQ-1, OQ-13, OQ-14, OQ-24): `entry_time` required for both types; nothing dated after today (São Paulo, injected clock); a trade may be dated up to the maturity date inclusive (on it the PU is typed and the rate stored as 0), never after; bounds are only the schema CHECKs. Execution PU/rate are stored on the immutable trade. Ledger never creates reference prices.
- A write only saves the fact and never enqueues work: Ledger calls no Processing contract and marks nothing (OQ-31). Processed results stay as they are until the user processes again.

### Prices
- `PriceService.set_reference_price(request, *, uow) -> ReferencePriceRecord`: one row per (asset, date, source) (OQ-25). Adding a price where the (asset, date, source) row already exists deletes the current row and inserts the new one, with a new id, in the same Unit of Work (OQ-26 item 7).
- `PriceService.correct_reference_price(..., *, uow) -> ReferencePriceRecord`: an UPDATE in place, same id, `updated_at` set.
- `PriceService.remove_reference_price(..., *, uow) -> None`: DELETEs the row; with MANUAL gone, B3 becomes preferred.
- `PriceReader.get_preferred(asset_id, reference_date) -> ReferencePriceRecord | None`
- `PriceReader.get_preferred_many(asset_ids, dates) -> mapping`
- `ReferencePriceRecord` has no `revision` (OQ-25).
- Reference prices may be dated up to the maturity date inclusive (PU typed on it, rate 0), never after it or after today (OQ-1, OQ-14). After maturity the reference PU is 0 by definition and no observation exists.
- Preferred source order: MANUAL, then B3. Exactly the requested calendar date; no carry-forward. There are no revisions (OQ-25), and prices live only in this table (OQ-30): Portfolio's reads take each date's reference PU, rate and source from the current preferred price through `PriceReader`; no published row stores a PU or a source, so the price table is the traceability. Every set, correction and removal only saves the price: it calls no Processing contract, marks nothing (OQ-31), changes no quantity and never enqueues processing. Future bulk import can call the same PriceService via a separate RabbitMQ adapter.

### Portfolio
Pure domain calculators (`portfolio/domain/`, frozen dataclasses). Two independent chains read the same Ledger facts and never each other's output (OQ-21); the application layer maps `ledger.public.TradeRecord` onto Portfolio's own `Trade(asset_id, trade_date, trade_time, seq, signed_quantity, execution_pu, execution_rate)`, ordered by `(trade_date, trade_time, seq)` (OQ-13). A skipped day or misdated event raises the internal `AccountingError`, not a `DomainError`.
- **Positions chain** (no cash, no prices): `PositionsEngine.calculate_day(previous_state: PositionState, trades, date) -> PositionsDay` and `calculate_range(previous_state, trades, end_date) -> tuple[PositionsDay, ...]`. `PositionState(as_of, positions: tuple[OpenPosition, ...])` holds `OpenPosition(asset_id, quantity ≠ 0, average_entry_pu, average_entry_rate)`; `PositionDay(asset_id, previous_quantity, quantity, average_entry_pu, average_entry_rate, trades)` exists exactly for the expected assets (OQ-10), quantity 0 included, with averages `None` when flat. Averages are rounded at each day's close (PU 10 dp, rate 12 dp, OQ-3) and carried forward as stored, so one job over [A, B] equals several jobs that read the previous day back.
- **Cash chain** (no positions, no prices): `CashCalculator.calculate_day(previous_balance: CashBalance, trades, deposits: Decimal, withdrawals: Decimal, date) -> CashDay` and `calculate_range(previous_balance, trades, deposits: Mapping[date, Decimal], withdrawals: Mapping[date, Decimal], end_date) -> tuple[CashDay, ...]`. `deposits`/`withdrawals` are the day's totals, summed by the application from `LedgerReader.get_cash_movements` (`0` when none, never negative; a date absent from the maps means none). `CashDay(date, previous_cash_balance, trades_cash_flow, deposits, withdrawals, cash_balance)` with `trades_cash_flow = −Σ(signed_qty × execution_PU)`: one `cash_balances` row.
- **Valuation**: `ValuationCalculator.calculate_day(date, assets: Sequence[AssetValuationInput], cash_balance: Decimal | None) -> PortfolioValuation`. `AssetValuationInput(asset_id, quantity, maturity_date, reference_pu, reference_source)`: a PU and its source (MANUAL or B3) go together or not at all (OQ-9, OQ-25); past maturity the caller passes neither. Per asset `AssetValuation(asset_id, reference_pu, reference_source, financial_total = Q × reference_PU, status)` with `status` COMPLETE, MISSING or NOT_REQUIRED: Q ≠ 0 without a price is MISSING and `null`; Q = 0 is worth 0, NOT_REQUIRED; after maturity the PU is 0 by definition, COMPLETE, with no source (OQ-1). `PortfolioValuation(date, assets, positions_market_value, aum, status)`: the market value is `null` if any asset is MISSING (never a partial sum), and AUM = cash + market value, `null` when either side is missing. No multiplier (OQ-2).
- `PortfolioAccounting.calculate_day(previous_state: AccountingState, trades, deposits, withdrawals, date) -> AccountingDay(cash: CashDay, positions_day: PositionsDay)` and `calculate_range(previous_state, trades, deposits: Mapping[date, Decimal], withdrawals: Mapping[date, Decimal], end_date) -> tuple[AccountingDay, ...]` run both chains over the same days, for an ALL scope only; `AccountingState(as_of, cash_balance, positions)`.
- Predecessor readers, one per chain (OQ-21, OQ-22): `PortfolioReader.get_previous_positions(before_date)` → `PreviousPositionsDay(state, cumulative_pnl)` published for `before_date − 1` (the closing `PositionState` and the cumulative P&L), or none; it carries no reference PU: a POSITIONS run reads the D−1 PU from `PriceReader.get_preferred_many` (current preferred price, exact date; 0 after maturity) (OQ-9, OQ-30); `get_previous_cash(before_date)` → the `CashBalance` from the published `cash_balances` row of `before_date − 1`, or none. A POSITIONS job reads only the first, a CASH job only the second, an ALL job both. Whether that predecessor was processed is not a Portfolio flag: Processing reads it from `date_status` (OQ-23, OQ-31).
- `PortfolioQueryService.get_position_table(date) -> PositionTableView`
- `PortfolioQueryService.get_summary(date) -> PortfolioSummaryView`
- `PortfolioResultsWriter` writes one date at a time, inside that date's transaction (OQ-23): `write_positions_day(day: PositionsDay, valuation: PortfolioValuation, asset_pnl: Mapping[asset_id, AssetPnLResult], pnl: PortfolioPnLResult, *, uow)` for POSITIONS and `write_cash_day(day: CashDay, *, uow)` for CASH; ALL calls both in the same transaction. Each replaces the date's published rows (rows of assets no longer expected on the date are deleted, OQ-10) and recomputes that date's `aum` from the other chain's published value (OQ-21). There is no staging and no `publish_range` (OQ-23); Processing calls these through `public.py` and sets the date's status in the same transaction.
- Portfolio owns published `positions`, `position_metrics`, `portfolio_metrics` and `cash_balances` (OQ-8); daily quantities and average costs remain calculable with missing reference prices. AUM = cash (`cash_balances`) + sum signed position market values (`portfolio_metrics`), `null` when either side is missing; AUM has no status of its own, and reads expose it as a plain value next to the cash and positions statuses (OQ-28). No exposure or `total_equity` fields. Rows exist for D exactly for expected assets: Q[D−1] ≠ 0 or a trade on D, including quantity 0 (OQ-10). `position_metrics` stores no reference PU and no source (OQ-30): it keeps the computed `financial_total` and P&L; `PortfolioResultsWriter` does not persist the valuation's PU or source. The position table read model takes each asset's reference PU, rate and source for the date from `PriceReader.get_preferred_many` (current preferred price: MANUAL, else B3, exact date; after maturity the PU is 0, with no source). After a price correction the date shows the new PU next to the old published figures and keeps its positions status until the user reprocesses it (OQ-30, OQ-31). Read models report each date's cash and positions statuses and their processing times (`cash_processed_at`, `portfolio_processed_at`) from `date_status` (OQ-23, OQ-31).

### PnL
- `AssetPnLCalculator.calculate(previous_position, day_trades, previous_reference_pu, current_reference_pu) -> AssetPnLResult`
- `PortfolioPnLCalculator.aggregate(expected_assets, asset_results, previous_cumulative) -> PortfolioPnLResult`
- Pure functions; no persistence or messaging adapters required initially.
- First day: when Q[D−1] = 0, `position_pnl` is exactly 0 and needs no D−1 price (OQ-4). After maturity the current reference PU is 0 (OQ-1). Precision: 34-digit `Decimal`, `ROUND_HALF_UP` (OQ-3). The multiplier is not applied (OQ-2).
- P&L uses daily Position P&L + Trades P&L attribution; deposits/withdrawals do not enter P&L. Missing required price => incomplete/null P&L, never silently zero or sum just available assets. Cumulative chain unavailable after an unresolved gap.

### Processing
- There is no `FinancialResultInvalidator` (OQ-31): `trades_changed`, `cash_movements_changed` and `prices_changed` are removed. Ledger and Prices writes do not call Processing, and nothing is ever marked stale. There are no revision counters and no dirty markers (OQ-23).
- `processing.date_status(date, portfolio, cash, portfolio_previous, cash_previous, portfolio_processed_at, cash_processed_at)` is the single source of each date's processing status (OQ-23, OQ-31); the `*_previous` columns hold a chain's status while it is `RUNNING`, so it can be put back (OQ-26). Per date and chain: NULL or no row = not processed (Não processado), `PROCESSED` (Processado), `PROCESSED_WITH_ISSUES` (Processado com pendências), `RUNNING` (Processando), `FAILED` (Erro; the date keeps its previously published data). `cash_processed_at` and `portfolio_processed_at` (TIMESTAMPTZ) are set when a run commits that chain for the date, NULL when it was never processed (OQ-31). Processing exposes it to Portfolio's read models as `DateStatusReader.get_date_statuses(start_date, end_date) -> Mapping[date, DateStatus(date, portfolio, cash, portfolio_processed_at, cash_processed_at)]` in `processing/public.py`; a date with no row is absent (not processed).
- `ProcessingService.preview_range(scope, start_date, end_date) -> ProcessingPreview` — the range is exactly [start, end] (OQ-11); the preview reports, per chain of the scope, the `date_status` of start−1 and warns when it is neither `PROCESSED` nor `PROCESSED_WITH_ISSUES` nor the chain's zero state, since the run would then fail on its first date (OQ-31). `scope` ∈ {CASH, POSITIONS, ALL} (OQ-21).
- `ProcessingService.enqueue_range(scope, start_date, end_date, *, uow) -> ProcessingRequest`
- `ProcessingService.request_cancel(request_id, *, uow) -> ProcessingRequest`
- `ProcessingService.list_requests(limit, cursor)` (keyset pagination on `(created_at, id)`), `get_request(id)`, `get_issues(...)`
- `ProcessingRequest` is the run, one row of `processing.requests` (OQ-23): `id`, `scope`, `start_date`, `end_date`, `status` (eight statuses, no `SUPERSEDED`), `progress_date` (the last date the run committed), `error_code`, `error_message`, `created_at`, `updated_at`, `dispatched_at`, `started_at`, `finished_at`, `cancel_requested_at`. Days done and total derive from the range and `progress_date`. Claim token and lease stay inside Processing.
- `ProcessingDispatcher.dispatch_next() -> Optional[request_id]`: transactionally claim singleton `calculation_state` row, set job DISPATCHED, record outbox command.
- `PortfolioRangeProcessor.run(request_id, claim_token)`: claim/lease (60 s, renewed per date, OQ-5); process exactly the requested dates (OQ-11), in calendar order, from `start_date`, or from the day after `progress_date` on recovery. For each date D, for the chains of the scope (OQ-23):
  1. a short transaction, under a row lock on the run's `processing.requests` row that checks the claim token and lease, keeps the chain's status on D in `*_previous` and sets it to `RUNNING` (both chains for ALL); a date with no row gets one with `*_previous` NULL; a chain already `RUNNING` (recovery) keeps its `*_previous` untouched;
  2. D's transaction locks the run's `requests` row (claim token and lease checked) and the `date_status` rows of D−1 and D in ascending date order, checks the predecessor rule below (for ALL, for both chains), computes D (CASH: `CashCalculator`; POSITIONS: `PositionsEngine`, Prices, `ValuationCalculator`, PnL; ALL: both), writes D through `PortfolioResultsWriter` (which recomputes D's AUM), replaces the positions issues for D (deletes the earlier `MISSING_REFERENCE_PRICE` and `EXPIRED_OPEN_POSITION` of that date and writes the new ones, OQ-26; the cash chain raises no issue, OQ-31), sets `requests.progress_date = D`, sets D's status (below) and the chain's `*_processed_at`, and commits. For ALL both chains and the AUM of D are in this one transaction.
  - **Predecessor rule, per day (OQ-31):** a run may start on any date. Before computing D, for each chain of the scope, D−1 must be `PROCESSED` or `PROCESSED_WITH_ISSUES`, or the chain's zero state (positions: no TRADE dated on or before D−1; cash: no entry of either type dated on or before D−1, OQ-26 item 3, OQ-32). A `FAILED` D−1 counts as not processed. Otherwise D is handled as a failure at D (below) with `error_code` `CASH_PREDECESSOR_MISSING` or `POSITIONS_PREDECESSOR_MISSING` and the pt-BR message "Dia anterior não processado": D gets `FAILED`, the run ends `FAILED` and later dates are not touched. Since dates run in order, this can only happen on a run's first date.
  - **ALL run (OQ-31 item 7):** D's predecessor check covers both chains. If either fails, nothing is written for D: each failing chain gets `FAILED` on D, the other chain goes back to its `*_previous` status, and the run ends `FAILED`. If both chains fail, `error_code` = `POSITIONS_PREDECESSOR_MISSING`.
  - **Status of D:** `PROCESSED`, or `PROCESSED_WITH_ISSUES` when D has a missing price or an expired open position; the chain's `*_processed_at` is set to the commit's time (OQ-31).
  - A write landing during the run only saves its fact and marks nothing; the run never stops for it (OQ-31).
  - **Failure at D:** D's transaction rolls back; a short transaction, fenced by the claim token like every worker write, sets the chain's status on D to `FAILED` (clearing `*_previous`; on an ALL run, a predecessor failure sets `FAILED` only on the failing chain(s), and the other chain is restored from `*_previous`, OQ-31 item 7) and stores `error_code` and `error_message` on the run, which ends `FAILED`. Later dates are not touched.
  - **A date left `RUNNING`:** whenever a run ends without committing a date it set `RUNNING` (cancel, or finalization after a lost lease; a failure at D sets D `FAILED` instead), that date's chain status is restored from `*_previous`; if that leaves both chains of the date without a status, the row is deleted (OQ-26).
  - Every worker write — `RUNNING`, the date's transaction, `FAILED`, the run's error and end status — checks the claim token and lease under a row lock on the run's `requests` row, in the same transaction, so a fenced-out worker changes nothing.
  - **End:** `COMPLETED`, or `COMPLETED_WITH_ISSUES` when a date it wrote is `PROCESSED_WITH_ISSUES`.
  - No nested RabbitMQ message per asset or per day.
- Issue types: `MISSING_REFERENCE_PRICE` and `EXPIRED_OPEN_POSITION` (OQ-31); there is no `STALE_PREDECESSOR` and `processing.issues` has no `chain` column. A missing predecessor is an error on the run, not an issue.
- The predecessor rule is checked per day (above), never at enqueue: enqueueing is never refused for it (OQ-31, replacing the refusal at start of OQ-22 and OQ-30).
- There is no cancel-and-replace (OQ-30): the user cancels, or queues a new request, as separate actions.
- Cancellation of queued work is immediate. Cancelling a `DISPATCHED` run moves it to `CANCELLING` and sets `cancel_requested_at`; the worker ends it `CANCELLED` when it claims it, processing no date. Cancelling a `CANCELLING` or finished run answers 409 `JOB_NOT_CANCELLABLE` (OQ-29). A running cancellation sets `cancel_requested_at`; the worker checks it between dates: the current date commits, later dates are not touched, and the run ends `CANCELLED`. A cancel that arrives during the last date lets the run end `COMPLETED`, or `COMPLETED_WITH_ISSUES` when a date it wrote has issues (OQ-23, OQ-26). Overlapping requests allowed in PostgreSQL, one active global job.

## Transaction boundaries and behavior

1. **Mutation:** HTTP handler opens UoW; Ledger or Prices writes the authoritative record; one COMMIT; return response. Nothing else: no invalidation and no automatic processing job (OQ-31).
2. **Enqueue:** HTTP handler opens UoW; Processing validates requested dates; insert `requests(status=QUEUED)`; COMMIT; return job ID. Do not publish one Rabbit message per enqueued job.
3. **Dispatch:** dispatcher under row lock selects oldest eligible QUEUED request by (created_at, id), sets singleton active ID and DISPATCHED, saves outbox command in same transaction, COMMIT. Outbox relay publishes with confirms.
4. **Execute, one date per transaction (OQ-23):** worker claims the specific dispatched job using claim token and time-bounded lease. For each date: a short transaction sets the date's chain status `RUNNING`; then the date's transaction locks the run's `requests` row and the `date_status` rows of D−1 and D in ascending date order, verifies the claim token and lease, checks the predecessor rule, upserts D's published rows and AUM, sets D's status, the chain's `*_processed_at` and `requests.progress_date`, and commits. There is no staging and no range-wide publish. Processing controls transaction durations; calculators have no DB side effects.
5. **Cancel:** a `QUEUED` job is cancelled at once; a `DISPATCHED` one moves to `CANCELLING` and the worker ends it `CANCELLED` when it claims it; for a `RUNNING` one the cancel flag is committed and the worker checks it between dates: the current date commits, later dates are not touched, the run ends `CANCELLED`; a `CANCELLING` or finished job answers 409 `JOB_NOT_CANCELLABLE` (OQ-29).
6. **Failure and recovery:** a failing date's transaction rolls back; a short transaction sets that date `FAILED` and stores the error on the run, which ends `FAILED`; later dates are not touched and earlier ones stay published. After a crash or a lost lease, recovery is explicit and resumes after `requests.progress_date`; the claim token stops a fenced-out worker from committing a date.
7. **Broker semantics:** RabbitMQ delivery at-least-once. Inbox idempotency plus request/status/claim fencing guards duplicate delivery. ACK only after durable state transition. Retries transient only; domain missing prices are `COMPLETED_WITH_ISSUES`, not retries. Relay and dispatcher recover after crashes.

**Date-status rule (OQ-23, OQ-31):** `processing.date_status` is the only source of each date's processing status; there is no staleness, no dirty markers and no revision counters. Every Portfolio read reports, for each date, the cash and positions statuses and their processing times from it (no row = not processed). A write changes no status: a processed date keeps its status and time until the user processes it again; dates after a processed range stay not processed until they are processed.

## HTTP endpoints

Paginated lists take `?limit=&cursor=` and return `{items, next_cursor}`, with keyset cursors: `(entry_date, entry_time, seq)` for ledger entries and `(created_at, id)` for processing requests (OQ-26).

- `GET /health` (and `HEAD`): `200 {"status": "ok"}` when PostgreSQL answers `SELECT 1` within a short timeout (2 s); otherwise `503` problem+json ("Serviço indisponível", "O banco de dados não está acessível."), nothing of the error in the body. Served by `composition/health.py`; the app is built by `di1.main:create_app` (uvicorn `--factory`).
- `GET /ledger/entries?start_date=&end_date=&search=&order=&limit=&cursor=` (paginated, both types), `POST /ledger/entries` (a trade or a cash movement), `POST /ledger/entries/deletions` with `{ids}` (hard delete in one transaction, all or nothing; 404 `NOT_FOUND` and nothing deleted when any id is unknown or already deleted; OQ-24, OQ-32). They replace `/trades` and `/cash-movements`. A trade item may expose its computed cash effect as `cash_amount`.
- `POST /reference-prices` (adds a price; an existing one for the same asset, date and source is deleted first, OQ-26 item 7; this is how the UI's Corrigir works), `GET /reference-prices`, `DELETE /reference-prices/{id}` (deletes the row, OQ-25). The HTTP shapes are those of the frontend contract in PR #41 (`frontend/src/api/contract/*`), with the corrections agreed with lane I (OQ-26 item 8)
- `GET /portfolio/positions?date=YYYY-MM-DD`, `GET /portfolio/summary?date=YYYY-MM-DD`, `GET /portfolio/pnl?start_date=&end_date=` (the published `portfolio_metrics` series, positions chain only, as `PnLPointView(date, daily_pnl, cumulative_pnl, range_cumulative_pnl, pnl_status, status, published_at)`; feeds the Carteira cumulative chart, no per-asset data; OQ-16; the chart calls it with `end_date` = the Carteira date and a user-chosen earlier `start_date`, OQ-27). Each portfolio read (summary, positions) carries the date's cash and positions statuses and their processing times (`cash_processed_at`, `portfolio_processed_at`) from `date_status` (OQ-23, OQ-31).
  - **P&L series (OQ-31 item 8):** each point carries only the positions chain's `status` and processing time (`published_at`). `range_cumulative_pnl` = Σ `daily_pnl` from the requested `start_date` to D, the start's own daily P&L included; the backend sums it from the published rows on each request. It is `null` from the first date in the range whose `daily_pnl` is null or that has no published positions day. The Carteira "P&L acumulado" chart draws `range_cumulative_pnl`; the frontend only draws it. The stored since-inception `cumulative_pnl` stays in the point and in the KPIs.
  - In every Portfolio read, a chain's processing time is the field `published_at` (the HTTP name in lane I's contract, kept): it is that chain's `*_processed_at` from `date_status`, shown as "Processado em dd/mm/aaaa hh:mm" (OQ-31). Lane I's `frontend/src/api/contract/portfolio.ts` still has the pre-OQ-31 statuses and must be updated to `PROCESSED`, `PROCESSED_WITH_ISSUES`, `RUNNING`, `FAILED`, `NOT_PROCESSED`.
- `POST /processing/requests`, `GET /processing/requests` (paginated), `GET /processing/requests/{id}`, `POST /processing/requests/{id}/cancel` (no cancel-and-replace route, OQ-30)
- `GET /instruments`, `POST /instruments`, `GET /products`, `POST /products` (`search`: substring, case- and accent-insensitive; products on code, name and asset class name, instruments on code; `Instrument.last_reference` is `null` for now, OQ-33); direct `POST /pricing/calculate` for previews if needed (the current UI shows no preview: the complementary PU or rate is computed when an entry is saved, OQ-19).
- **UI read needs (OQ-19, OQ-20).** The frontend's draft contract (lane I) proposes how each is served; the integrator fixes route names and shapes:
  - Pendências list: an HTTP route for `ProcessingService.get_issues`, two issue types only (`MISSING_REFERENCE_PRICE`, `EXPIRED_OPEN_POSITION`; OQ-31).
  - Range preview: an HTTP route for `ProcessingService.preview_range` (scope, exact [A, B], number of days, and per chain of the scope the `date_status` of start−1; a cash start−1 not processed and not the zero state warns that the run will fail on its first date with `CASH_PREDECESSOR_MISSING`, and positions with `POSITIONS_PREDECESSOR_MISSING`; OQ-21, OQ-23, OQ-31).
  - Processing request read: `id`, `scope`, `start_date`, `end_date`, status (eight, no `SUPERSEDED`), `progress_date` (days done and total derive from it and the range), created/started/finished/updated times, `error_code` and `error_message`, if any (OQ-23). "Solicitar novo processamento" prefills from the failed date, or, for a cancelled run, from the first date it did not reach, to the original end. There is no "Cancelar e criar novo processamento": cancel and queue are separate actions (OQ-30).
  - Ativos catalogue: instrument types and asset classes, and per product its class, type and number of contracts.
  - Contract list: per instrument, its latest reference observation `{date, pu, rate, source}`, or `null`.
  - Reference prices: the source of each observation; there is no revision history (OQ-25).
  - Carteira position table: each asset's reference PU, rate and source for the date come from the current preferred price in the price table, not from `position_metrics` (OQ-30).
  - Ledger entries: each trade with both execution PU and execution rate.
  - Lançamentos cash strip: `GET /portfolio/summary` for the range end date and the day before; the cash comes from `cash_balances`, with the date's cash status and `cash_processed_at` from `date_status` (OQ-21, OQ-23, OQ-31).
  - Processing scope: the request form and list carry `scope` (CASH, POSITIONS, ALL; UI labels Caixa, Posições, Tudo), and the summary reports the date's cash and positions statuses and processing times separately, from `date_status` (OQ-21, OQ-23, OQ-31).
- All UI-facing content/labels in pt-BR; schema, internal interfaces, and Python identifiers remain English.

### Errors (OQ-15)

Every error response is RFC 9457 `application/problem+json`:

```json
{"type": "about:blank", "title": "…", "status": 422, "detail": "…",
 "errors": [{"code": "FUTURE_DATE", "message": "A data não pode ser posterior a hoje.", "field": "entry_date"}]}
```

`message` is pt-BR; `code` is English. Catalogue (extended additively by the integrator):

| Code | Status | Meaning |
|---|---|---|
| `VALIDATION_ERROR` | 422 | Malformed or out-of-bounds input (schema CHECK rules, too many decimals) |
| `FUTURE_DATE` | 422 | An entry or price dated after today (São Paulo), or a processing range (request, preview) ending after today (OQ-29) |
| `CONTRACT_MATURED` | 422 | A trade or reference price dated after the instrument's maturity |
| `NOT_FOUND` | 404 | The resource in the URL path does not exist. An unknown id in the request body (e.g. `product_id`, `asset_class_id`) is a 422 `VALIDATION_ERROR` on that field (OQ-33). Exception: the `ids` of `POST /ledger/entries/deletions` are the resources being deleted, so an unknown or already-deleted id answers 404 and nothing is deleted (OQ-32) |
| `INVALID_RANGE` | 422 | A processing or query range with start after end |
| `JOB_NOT_CANCELLABLE` | 409 | Cancel requested for a job that is already `CANCELLING` or finished (OQ-29) |

## DI composition

`modules/<name>/public.py` exposes stable read/service contracts and DTOs; `modules/<name>/dependencies.py` creates module-local implementations; `composition/dependencies.py` wires cross-module collaborators and UoW; `composition/routers.py` registers routes; `composition/consumers.py` registers handlers; workers use plain factories, not FastAPI `Depends`. No one-class-per-command framework; cohesive application services.
