# Maravi DI1 — Module contracts and execution boundaries

**Status:** implemented on `main` (decisions up to OQ-46, 2026-10-19). **OQ-50 (2026-10-19) is decided and implemented in later PRs on `simplify`:** AUM computed at read time, one RabbitMQ message per request plus a periodic sweep (no doorbell, no inbox), a stale-price mark in Carteira, and "Processando" derived instead of stored. The passages it changes carry a "Since OQ-50" note; until each PR lands, the code follows the older text. Consistent with `schema.md` (2026-10-19). This document specifies service ownership and call semantics, not actual Python implementations.

## Scope and structural rules

Single portfolio (no `portfolio_id`). Modular monolith: `asset`, `ledger`, `pricing`, `prices`, `portfolio`, `pnl`, `processing`. HTTP/API service methods may be async; calculation engines are deterministic synchronous pure Python. `platform` owns database session/UoW, RabbitMQ/outbox/inbox, tracing. Cross-module access only through `public.py` contracts. No service imports another module's repositories/ORM. `Depends` only in FastAPI adapters/dependency providers. SQL lives in `infrastructure/persistence/queries`. A business mutation saves only the fact, in one Unit of Work; there is no financial-result invalidation (OQ-31).

## Contract catalog

### Asset
- `AssetReader.get_instruments(ids) -> Mapping[id, Instrument]` (unknown ids absent). A caller that needs 404 (Pricing) raises it.
- `AssetService.create_product(asset_class_id, code, name, futures)`, `create_instrument(product_id, code, maturity_date)`, `get_instrument(...)`, `list_instruments(...)`
- `Instrument`: id, code, product_id, product_code, instrument_type, asset_class, maturity_date, face_value, multiplier, settlement_method.
- Asset normalises `code` (trim + upper-case) before validating and storing it; uniqueness is case-insensitive (OQ-33).
- `Instrument.last_reference` on the Asset HTTP reads is filled by the Asset router from `prices.public.PriceReader.latest` (below), injected by composition: each instrument's latest winning reference price as `{reference_date, pu, rate, source}`, or `null` when it has none (OQ-48, reversing OQ-33 item 4). The catalogue service does not know about prices.
- Asset validates product/class/type hierarchy and maturity requirements. Futures' shared specs in `asset.futures`, contract maturity in `asset.instruments`.

### Pricing
- `PricingService.calculate(instrument_id, reference_date, quote: Quote) -> Price`: the service reads the instrument through `asset.public.AssetReader.get_instruments` and builds the calculator's terms from it, so no caller passes a stale face value (lane B's approved contract request). An unknown id is `NOT_FOUND` from Pricing. It prices only instruments of product code `DI1` (case-insensitive); another product, or an instrument without a maturity or a face value, is 422 `VALIDATION_ERROR` on `asset_id` (OQ-34).
- Pricing's error `field` names are `asset_id`, `reference_date`, `pu` and `rate`; each caller remaps them to its own request fields (Ledger: `date`, `execution_pu`, `execution_rate`; Prices: unchanged (its request fields already use these names)). The calculator raises `DomainError` directly (OQ-34).
- `QuoteValidator(fields: QuoteFields = QuoteFields())` is the one validation of a typed quote (code-review H3): pure and synchronous, `(kind, *, pu, rate, reference_date, maturity_date) -> (typed value | None, errors)`. It covers one typed value, decimals (OQ-3), bounds (OQ-14) and maturity (OQ-1); `QuoteFields` names the error fields and `from_pricing` renames the calculator's. The calculator runs it too; Ledger's and Prices' domain functions take it as an injected `QuoteRule` (domain imports no other module), passed by their services.
- `Quote` is what was typed, the single authoritative input: a rate or a PU. `Price` is the complete pair: PU, rate and input_kind, neither optional. The only convention is DC/365 (spec §4.1).
- `DI1Calculator` is pure and returns a value. Calculators never publish messages or persist results. `PriceService` and `LedgerService` can both call Pricing's public interface; P&L does **not** belong here.

### Ledger
One table, `ledger.entries` (OQ-24): each entry is a TRADE or a CASH movement, with `entry_date`, `entry_time` (required, São Paulo local time) and one `seq` shared by both types. The order is `(entry_date, entry_time, seq)` across both types. A CASH entry stores a signed `cash_amount` (positive aporte, negative retirada, never 0) and an optional `description` (trimmed, at most 200 characters, blank → `null`; a TRADE has none, OQ-51); a trade's cash effect is not stored, it is computed on read as −`signed_quantity` × `execution_pu` by the single function in the portfolio cash domain.
- `LedgerService.create_entry(request, *, uow) -> LedgerEntry` (a trade or a cash movement)
- `LedgerService.delete_entries(ids, *, uow) -> None`: a hard delete (OQ-32), a real `DELETE` from `ledger.entries` of one or many entries of either type, with no reason, in one transaction, all or nothing. If any id is unknown (or already deleted, which is the same thing), it raises the not-found error (HTTP 404 `NOT_FOUND`) and nothing is deleted. An empty `ids` is a validation error (422 on `ids`); a repeated id counts once (OQ-32 item 5). There is no audit trail: a deleted entry no longer exists anywhere, and processed results keep their figures until the user processes the dates again (OQ-31).
- `LedgerService.list_entries(start_date, end_date, search, order, limit, cursor) -> page of LedgerEntry`, the read behind `GET /ledger/entries` (keyset pagination on `(entry_date, entry_time, seq)`, OQ-26; method name integrator-defined).
- `LedgerReader.get_trades(start_date, end_date) -> ordered list[LedgerEntry]` and `LedgerReader.get_cash_movements(start_date, end_date) -> ordered list[LedgerEntry]` keep their names and read the entries of `ledger.entries` of their type (every row is a live entry; there is no deleted state to filter, OQ-32), in `(entry_date, entry_time, seq)` order. A CASH `LedgerEntry` carries the time, the `seq` and the signed amount (OQ-24).
- `ledger.public` exports `EntryType` (`TRADE`, `CASH`) and `LedgerReader.has_entries_on_or_before(day, *, entry_type: EntryType | None = None) -> bool` (OQ-37): `None` counts entries of both types (the cash zero state), `TRADE` counts trades (the positions zero state); Processing uses it for the OQ-31 zero-state check. Lane C implements it.
- Writes validate Asset and use Pricing when a trade is rate-only or PU-only. Validation (OQ-1, OQ-13, OQ-14, OQ-24): `entry_time` required for both types; nothing dated after today (São Paulo, injected clock); a trade may be dated up to the maturity date inclusive (on it the PU is typed and the rate stored as 0), never after; bounds are only the schema CHECKs. Execution PU/rate are stored on the immutable trade. Ledger never creates reference prices.
- A write only saves the fact and never enqueues work: Ledger calls no Processing contract and marks nothing (OQ-31). Processed results stay as they are until the user processes again.

### Prices
- `PriceService.set_reference_price(asset_id, reference_date, input_kind, pu, rate, *, source=MANUAL, uow) -> ReferencePriceRecord`: one row per (asset, date, source) (OQ-25). Adding a price where the (asset, date, source) row already exists deletes the current row and inserts the new one, with a new id, in the same Unit of Work (OQ-26 item 7). Persistence does that as one `INSERT … ON CONFLICT DO UPDATE` that assigns a new id (atomic; two concurrent writes of the same key leave one row). There is no in-place UPDATE and no `correct_reference_price`.
- `PriceService.remove_reference_price(..., *, uow) -> None`: DELETEs the row; with MANUAL gone, B3 becomes preferred.
- `PriceReader.get(asset_ids, dates) -> Mapping[(asset_id, date), ReferencePriceRecord]`: MANUAL before B3 on each exact date; pairs without a price are absent. No source filter (spec §5).
- `PriceReader.latest(asset_ids) -> Mapping[asset_id, ReferencePriceRecord]` (OQ-48): per asset, the winning price on the latest date that has one; assets without a price are absent. No cap at today: no price is dated after today (OQ-14). Asset HTTP uses this for `Instrument.last_reference`; it is shown with its own date, never as today's price (OQ-19).
- `ReferencePriceRecord` has no `revision` (OQ-25).
- Reference prices may be dated up to the maturity date inclusive (PU typed on it, rate 0), never after it or after today (OQ-1, OQ-14). After maturity the reference PU is 0 by definition and no observation exists.
- Preferred source order: MANUAL, then B3. Exactly the requested calendar date; no carry-forward. There are no revisions (OQ-25), and prices live only in this table (OQ-30): Portfolio's reads take each date's reference PU, rate and source from the current preferred price through `PriceReader`; no published row stores a PU or a source, so the price table is the traceability. Every set and removal only saves the price: it calls no Processing contract, marks nothing (OQ-31), changes no quantity and never enqueues processing. Future bulk import can call the same PriceService via a separate RabbitMQ adapter.

### Portfolio
Pure domain calculators (`portfolio/domain/`, frozen dataclasses). Two independent chains read the same Ledger facts and never each other's output (OQ-21); the application layer maps `ledger.public.LedgerEntry` onto Portfolio's own `Trade(asset_id, trade_date, trade_time, seq, signed_quantity, execution_pu, execution_rate)`, ordered by `(trade_date, trade_time, seq)` (OQ-13). A skipped day or misdated event raises the internal `AccountingError`, not a `DomainError`.
- **Positions chain** (no cash, no prices): `PositionsEngine.calculate_day(previous_state: PositionState, trades, date) -> PositionsDay`. `PositionState(as_of, positions: tuple[OpenPosition, ...])` holds `OpenPosition(asset_id, quantity ≠ 0, average_entry_pu, average_entry_rate)`; `PositionDay(asset_id, previous_quantity, quantity, average_entry_pu, average_entry_rate, trades)` exists exactly for the expected assets (OQ-10), quantity 0 included, with averages `None` when flat. Averages are rounded at each day's close (PU 10 dp, rate 12 dp, OQ-3) and carried forward as stored, so one job over [A, B] equals several jobs that read the previous day back.
- **Cash chain** (no positions, no prices): `CashCalculator.calculate_day(previous_balance: CashBalance, trades, deposits: Decimal, withdrawals: Decimal, date) -> CashDay`. `deposits`/`withdrawals` are the day's totals, summed by the application from `LedgerReader.get_cash_movements` (`0` when none, never negative). `CashDay(date, previous_cash_balance, trades_cash_flow, deposits, withdrawals, cash_balance)` with `trades_cash_flow = −Σ(signed_qty × execution_PU)`: one `cash_balances` row. A published read has `previous_cash_balance` `None` (that figure is not stored).
- **Valuation**: `ValuationCalculator.calculate_day(date, assets: Sequence[AssetValuationInput]) -> PortfolioValuation`. `AssetValuationInput(asset_id, quantity, maturity_date, reference_pu)`: the exact-date preferred PU or none; past maturity the caller passes none. Per asset `AssetValuation(asset_id, reference_pu, financial_total = Q × reference_PU, status)` with `status` COMPLETE, MISSING or NOT_REQUIRED: Q ≠ 0 without a price is MISSING and `null`; Q = 0 is worth 0, NOT_REQUIRED; after maturity the PU is 0 by definition, COMPLETE (OQ-1). `PortfolioValuation(date, assets, positions_market_value, status)`: the market value is `null` if any asset is MISSING (never a partial sum). AUM is not computed here: the writer's repository recomputes it from both published chains (below). No multiplier (OQ-2). Since OQ-50 item 1: nothing writes AUM; the reads compute it.
- **Maturity**: `is_past_maturity(day, maturity)` and `reference_pu_on(day, maturity, price_pu)`, the one rule for the reference PU that valuation, P&L and the position table share: the exact-date price (or none) up to and including the maturity date, 0 after it whatever price exists (spec §7.4, OQ-1).
- Predecessor readers, one per chain (OQ-21, OQ-22): `PortfolioReader.get_previous_positions(before_date)` → `PreviousPositionsDay(state, cumulative_pnl)` published for `before_date − 1` (the closing `PositionState` and the cumulative P&L), or none; it carries no reference PU: a POSITIONS run reads the D−1 PU from `PriceReader.get` (winning price, exact date; 0 after maturity) (OQ-9, OQ-30); `get_previous_cash(before_date)` → the `CashBalance` from the published `cash_balances` row of `before_date − 1`, or none. A POSITIONS job reads only the first, a CASH job only the second, an ALL job both. Whether that predecessor was processed is not a Portfolio flag: Processing reads it from `date_status` (OQ-23, OQ-31).
- `PortfolioService.get_position_table(date) -> PositionTableView`
- `PortfolioService.get_summary(date) -> PortfolioSummaryView`
- `PortfolioResultsWriter` writes one date at a time, inside that date's transaction (OQ-23): `write_positions_day(day: PositionsDay, valuation: PortfolioValuation, asset_pnl: Mapping[asset_id, AssetPnLResult], pnl: PortfolioPnLResult, *, uow, other_chain_processed: bool)` for POSITIONS and `write_cash_day(day: CashDay, *, uow, other_chain_processed: bool)` for CASH; ALL calls both in the same transaction. Each replaces the date's published rows (rows of assets no longer expected on the date are deleted, OQ-10) and recomputes that date's `aum` from the other chain's published value (OQ-21). `other_chain_processed` is Processing's answer for the other chain on that date, derived from that chain's `date_status` on the date, whichever run wrote it (`PROCESSED` or `PROCESSED_WITH_ISSUES`); when `False` (`FAILED`, `RUNNING` or not processed) the written `aum` is `null` (OQ-38, OQ-40). This holds on every date of an ALL run after one chain stopped. On ALL the first call passes `False` and the second, made after both chains are computed, passes the first chain's outcome, so AUM never sees a chain `RUNNING`. There is no staging and no `publish_range` (OQ-23); Processing calls these through `public.py` and sets the date's status in the same transaction. **Since OQ-50 item 1:** AUM is not stored. The writers drop `other_chain_processed` and no longer recompute `aum`; `get_summary` (and any read that shows AUM) computes `cash_balance + positions_market_value` for the date only when both chains' `date_status` are `PROCESSED` or `PROCESSED_WITH_ISSUES`, else `null`.
- Portfolio owns published `positions`, `position_metrics`, `portfolio_metrics` and `cash_balances` (OQ-8); daily quantities and average costs remain calculable with missing reference prices. AUM = cash (`cash_balances`) + sum signed position market values (`portfolio_metrics`), `null` when either side is missing or the other chain of the date is not `PROCESSED` or `PROCESSED_WITH_ISSUES` (`FAILED`, `RUNNING` or not processed), whichever run wrote that chain (OQ-38, OQ-40); AUM has no status of its own, and reads expose it as a plain value next to the cash and positions statuses (OQ-28). No exposure or `total_equity` fields. Rows exist for D exactly for expected assets: Q[D−1] ≠ 0 or a trade on D, including quantity 0 (OQ-10). `position_metrics` stores no reference PU and no source (OQ-30): it keeps the computed `financial_total` and P&L; `PortfolioResultsWriter` does not persist the valuation's PU or source. The position table read model takes each asset's reference PU, rate and source for the date from `PriceReader.get` (current preferred price: MANUAL, else B3, exact date; after maturity the PU is 0, with no source). After a price correction the date shows the new PU next to the old published figures and keeps its positions status until the user reprocesses it (OQ-30, OQ-31). Read models report each date's cash and positions statuses and their processing times (`cash_processed_at`, `portfolio_processed_at`) from `date_status` (OQ-23, OQ-31). **Since OQ-50 item 3:** the position table marks a row whose current reference price of D or of D−1 (position P&L uses both; integrator reading) has `created_at` later than D's `portfolio_processed_at` ("Preço alterado após o processamento — reprocesse"; the field name is the implementing PR's choice); a re-saved price has a new id and `created_at` by design (OQ-25). **Since OQ-50 item 4:** a chain shows `RUNNING` (Processando) on a read only when the active run of that chain is on that date (`progress_date + 1`, or `start_date`); the stored status is never `RUNNING`.

### PnL
- `AssetPnLCalculator.calculate(previous_position, day_trades, previous_reference_pu, current_reference_pu) -> AssetPnLResult`
- `PortfolioPnLCalculator.aggregate(expected_assets, asset_results, previous_cumulative) -> PortfolioPnLResult`
- Pure functions; no persistence or messaging adapters required initially.
- First day: when Q[D−1] = 0, `position_pnl` is exactly 0 and needs no D−1 price (OQ-4). After maturity the current reference PU is 0 (OQ-1). Precision: 34-digit `Decimal`, `ROUND_HALF_UP` (OQ-3). The multiplier is not applied (OQ-2).
- P&L uses daily Position P&L + Trades P&L attribution; deposits/withdrawals do not enter P&L. Missing required price => incomplete/null P&L, never silently zero or sum just available assets. Cumulative chain unavailable after an unresolved gap.

### Processing
- There is no `FinancialResultInvalidator` (OQ-31): `trades_changed`, `cash_movements_changed` and `prices_changed` are removed. Ledger and Prices writes do not call Processing, and nothing is ever marked stale. There are no revision counters and no dirty markers (OQ-23).
- `processing.date_status(date, portfolio, cash, portfolio_previous, cash_previous, portfolio_processed_at, cash_processed_at)` is the single source of each date's processing status (OQ-23, OQ-31); the `*_previous` columns hold a chain's status while it is `RUNNING`, so it can be put back (OQ-26). Per date and chain: NULL or no row = not processed (Não processado), `PROCESSED` (Processado), `PROCESSED_WITH_ISSUES` (Processado com pendências), `RUNNING` (Processando), `FAILED` (Erro; the date keeps its previously published data). `cash_processed_at` and `portfolio_processed_at` (TIMESTAMPTZ) are set when a run commits that chain for the date, NULL when it was never processed (OQ-31). Processing exposes it to Portfolio's read models as `DateStatusReader.get_date_statuses(start_date, end_date) -> Mapping[date, DateStatus(date, portfolio, cash, portfolio_processed_at, cash_processed_at)]` in `processing/public.py`; a date with no row is absent (not processed). **Since OQ-50 item 4:** `RUNNING` is never written and `portfolio_previous`/`cash_previous` are unused; `DateStatusReader` (or the read side) derives `RUNNING` for the active run's current date, `progress_date + 1` (or `start_date`), for each chain of its scope still alive (integrator reading).
- `ProcessingService.preview_range(scope, start_date, end_date) -> ProcessingPreview` — the range is exactly [start, end] (OQ-11); the preview reports the `date_status` of start−1 for both chains (`predecessor.cash` and `predecessor.positions`) whatever the scope (OQ-39); only the scope's chains decide the warning, which the frontend applies when start−1 is neither `PROCESSED` nor `PROCESSED_WITH_ISSUES` nor the chain's zero state (no date before start has any status for the chain and no entry of the chain's type on or before start−1, OQ-40 item 5), since the run would then fail on its first date (OQ-31, OQ-39). `scope` ∈ {CASH, POSITIONS, ALL} (OQ-21).
- `ProcessingService.enqueue_range(scope, start_date, end_date, *, uow) -> ProcessingRequest`: saves the request `QUEUED` and, in the same transaction, writes one outbox message, a doorbell that only means "there is work"; its message type is `processing.run_request` with an empty payload (`{}`), written by `OutboxDoorbell` in `enqueue_range`'s transaction; the worker never reads a run from it (OQ-46). **Since OQ-50 item 2 (option 1):** the outbox message carries the request's `request_id` (one per request; for tracing and logs only, since the relay does not guarantee publication order); there is no doorbell.
- `ProcessingService.request_cancel(request_id, *, uow) -> ProcessingRequest`
- `ProcessingService.list_requests(limit, cursor)` (keyset pagination on `(created_at, id)`), `get_request(id)`, `get_issues(...)`
- `ProcessingRequest` is the run, one row of `processing.requests` (OQ-23): `id`, `scope`, `start_date`, `end_date`, `status` (eight statuses, no `SUPERSEDED`), `progress_date` (the last date the run committed; on an ALL run, for any chain, OQ-36), `error_code`, `error_message` (set when the run ends `FAILED`, and on `COMPLETED_WITH_ISSUES` or `CANCELLED` only when a chain of an ALL run failed, with the first failure's code and message; null otherwise, OQ-36), `failed_date: date | None` and `failed_chain: ProcessingScope | None` (the run's first failure: `failed_chain` is `CASH` or `POSITIONS`, never ALL; the chain that failed; `POSITIONS` when both chains of an ALL run fail on the same date, as OQ-36 item 5; on a single-chain run, the run's chain for a chain failure; null with a `failed_date` for a non-chain failure, on any scope; integrator choices; both null if the run never failed, and on a run aborted by a non-transient error that left no date `FAILED`, see "Failure and recovery" (integrator reading, #115); a `CANCELLED` ALL run keeps them, OQ-40 items 3 and 6), `created_at`, `updated_at`, `dispatched_at` (always null since OQ-46: there is no dispatch step), `started_at`, `finished_at`, `cancel_requested_at`. Days done and total derive from the range and `progress_date`. The unused `claim_token`, `lease_expires_at` and `attempt_count` columns are not exposed (OQ-45). Of the eight statuses, `DISPATCHED` and `CANCELLING` stay in the enum but are never set (OQ-46): a run goes `QUEUED` → `RUNNING`.
- There is no `ProcessingDispatcher` and no dispatcher process (OQ-46, replacing OQ-45 item 5). The single worker takes the work itself: `PortfolioRangeProcessor.take_next() -> UUID | None`, in one transaction, row-locks the oldest `QUEUED` request by `(created_at, id)`, sets it `RUNNING` with `started_at`, and commits; if the locked row is no longer `QUEUED` when the lock is granted (a cancel committed while it waited), it selects again, and it returns None only when no `QUEUED` row exists. On every doorbell message the worker runs `PortfolioRangeProcessor.drain()`, which repeats `take_next()` and runs the request it got until it gets None; at startup `recover_at_startup()` runs the recovery below and then `drain()`. Nothing is taken while a run is `RUNNING`, since the one worker runs serially; a doorbell that finds nothing `QUEUED` does nothing. PostgreSQL decides the order; a lost message is recovered by any later message or by a restart, and duplicates are harmless. Only one run is active at a time because there is one worker, which drains serially; `calculation_state.active_request_id` is not used as a slot and stays unused (integrator reading). A cancel of a `QUEUED` request and `take_next()` serialize on that row's lock: whichever commits first wins, and the other sees the new status (`take_next()` skips a row no longer `QUEUED`; the cancel of a now `RUNNING` run sets `cancel_requested_at`). These names follow the Processing code. **Since OQ-50 item 2:** on any run message the worker takes the oldest `QUEUED` request by `(created_at, id)`, row-locked, sets it `RUNNING` with `started_at` and runs it, or acks and does nothing when none is `QUEUED`; the message's `request_id` is not used to pick the run (FIFO by `(created_at, id)` unchanged, OQ-5 item 4). A periodic sweep in the worker, every few seconds (configurable), does the same take while anything is `QUEUED`. At startup, recovery (below) runs first, then the sweep. Method names are the implementing PR's.
- `PortfolioRangeProcessor.run(request_id)`: run by the single worker (OQ-45), with no lease and no claim token, on a run `take_next()` has just set `RUNNING` (OQ-46), or on the run recovered at worker start; it processes exactly the requested dates (OQ-11), in calendar order, from `start_date`, or from the day after `progress_date` on recovery; on an ALL run's recovery, a chain that has a `FAILED` date in [`start_date`, `progress_date`] for this run stays stopped and only the other chain continues, read from `date_status` with nothing new stored (OQ-36 item 9). For each date D, for the chains of the scope (OQ-23):
  1. a short transaction, under a row lock on the run's `processing.requests` row, keeps the chain's status on D in `*_previous` and sets it to `RUNNING` (both chains for ALL, or only the chain still alive once one has failed, OQ-36); a date with no row gets one with `*_previous` NULL; a chain is never already `RUNNING` here, since recovery at worker start restores the dates a run left `RUNNING` before it resumes (below) (flagged for the implementing PR, A1: since OQ-50 no date is written `RUNNING`, so nothing is restored); **Since OQ-50 item 4 this step is removed:** nothing is set `RUNNING`; step 2 takes D from its old status to its new one.
  2. D's transaction locks the run's `requests` row and the `date_status` rows of D−1 and D in ascending date order, checks the predecessor rule below (for ALL, for each chain still alive), computes D (CASH: `CashCalculator`; POSITIONS: `PositionsEngine`, Prices, `ValuationCalculator`, PnL; ALL: both), writes D through `PortfolioResultsWriter` (which recomputes D's AUM), replaces the positions issues for D (deletes the earlier `MISSING_REFERENCE_PRICE` and `EXPIRED_OPEN_POSITION` of that date and writes the new ones, OQ-26; the cash chain raises no issue, OQ-31), sets `requests.progress_date = D`, sets D's status (below) and the chain's `*_processed_at`, and commits. For ALL, while both chains are alive, both and the AUM of D are in this one transaction; there is no parallel execution (OQ-36).
  - **Predecessor rule, per day (OQ-31):** a run may start on any date. Before computing D, for each chain of the scope, D−1 must be `PROCESSED` or `PROCESSED_WITH_ISSUES`, or the chain's zero state: no date before D has any status for the chain (`PROCESSED`, `PROCESSED_WITH_ISSUES`, `RUNNING` or `FAILED`) **and** no entry of the chain's type is dated on or before D−1 (positions: no TRADE; cash: no entry of either type; OQ-26 item 3, OQ-32, OQ-40 item 5). The check, per chain (OQ-37 item 4): D−1 `PROCESSED`/`PROCESSED_WITH_ISSUES` → compute D; D−1 `FAILED` or `RUNNING` → fail D, Ledger not asked; D−1 with no status while an earlier date of the chain has one (a gap) → fail D, Ledger not asked (every day must be processed); only when the chain has no status on any date before D is Ledger asked (OQ-40 item 5), through `LedgerReader.has_entries_on_or_before(D−1, entry_type=EntryType.TRADE)` for positions and `has_entries_on_or_before(D−1)` for cash: `False` is the zero state (compute D), `True` fails D. Otherwise D is handled as a failure at D (below) with `error_code` `CASH_PREDECESSOR_MISSING` or `POSITIONS_PREDECESSOR_MISSING` and the pt-BR message "Dia anterior não processado": D gets `FAILED`, the run ends `FAILED` (on ALL, see below) and later dates are not touched. Since dates run in order, this can only happen on a run's first date.
  - **ALL run, one chain fails (OQ-36, replacing OQ-31 item 7):** D's predecessor check covers each chain still alive. When one chain fails on D, by the predecessor check or by a technical error, that chain gets `FAILED` on D and its later dates in the range are not touched; the other chain is still written on D, in the same transaction, and continues to the end of the range (OQ-36 item 8). D runs in one transaction with a SAVEPOINT per chain (OQ-40 item 1): a technical error in one chain rolls that chain back to its savepoint and sets it `FAILED`, the run keeps the first error, and the surviving chain's rows, AUM, `progress_date` and statuses commit in the same transaction, so no crash window opens between `FAILED` and `progress_date`. Any error raised by a chain's `PortfolioResultsWriter` call belongs to that chain; the writer recomputes D's AUM inside its own call. A non-chain failure is anything outside every chain's savepoint, for example a lock timeout on the date's `date_status` rows (the list is an integrator choice); it rolls back all of D: D is `FAILED` for every chain still alive in the run and the run ends `FAILED`; a chain that already stopped keeps OQ-36 item 1, its later dates are not touched. A worker crash is not a failure at D: the run resumes when the worker starts (OQ-45, replacing OQ-40's lost lease). A date's `aum` follows the other chain's status on that date, whichever run wrote it: `null` unless it is `PROCESSED` or `PROCESSED_WITH_ISSUES`, and when either side is missing (OQ-28, OQ-38, OQ-40). The run ends `COMPLETED_WITH_ISSUES` with `error_code` and `error_message` of the first failure, and `FAILED` only when both chains fail. If both fail on the same date, `error_code` = `POSITIONS_PREDECESSOR_MISSING` for the predecessor case, or the positions chain's error otherwise. CASH and POSITIONS runs are unchanged.
  - **Status of D:** `PROCESSED`, or `PROCESSED_WITH_ISSUES` when D has a missing price or an expired open position; the chain's `*_processed_at` is set to the commit's time (OQ-31).
  - A write landing during the run only saves its fact and marks nothing; the run never stops for it (OQ-31).
  - **Failure at D:** a failure of one chain (its predecessor check or a technical error inside the chain) is handled with that chain's SAVEPOINT inside D's transaction, on every scope (integrator choice, extending OQ-40 item 1): the chain rolls back to its savepoint, its status on D is set to `FAILED` (clearing `*_previous`) and `error_code` and `error_message` are stored on the run (`PROCESSING_ERROR`, "Erro técnico ao processar a data.", for a technical error, OQ-44; the predecessor codes for the predecessor check), all in D's transaction; there is no "roll back D, then a short transaction sets `FAILED`" for a chain failure. A single-chain run then ends `FAILED`. On an ALL run the first failure's error is kept, the other chain is still written on D in the same transaction and continues, and the run ends `COMPLETED_WITH_ISSUES` with that error, or `FAILED` only when both chains have failed (OQ-36); the chain's `FAILED` status on D, the error, the surviving chain's rows, AUM and `progress_date` commit together in D's transaction (OQ-40). A non-chain failure (outside every chain's savepoint), and an error that breaks the connection, which cannot use a savepoint, take the non-chain path: all of D rolls back, and a short transaction sets D `FAILED` for every chain still alive in the run (clearing `*_previous`), stores the error (`PROCESSING_ERROR`, OQ-44) with `failed_chain` NULL, and the run ends `FAILED` (integrator choice). The run's first failure is stored as `failed_date` and `failed_chain` (`POSITIONS` when both chains fail on the same date; the run's chain on a single-chain run; null for a non-chain failure; integrator choices, OQ-40). Later dates of the failed chain are not touched.
  - **A date left `RUNNING`:** whenever a run ends without committing a date it set `RUNNING` (a cancel, or a worker crash found at the next worker start, OQ-45; a failure at D sets D `FAILED` instead), that date's chain status is restored from `*_previous`; if that leaves both chains of the date without a status, the row is deleted (OQ-26). Since OQ-50 item 4 no date is left `RUNNING`, so there is nothing to restore.
  - **Recovery at worker start (OQ-45, replacing OQ-43's lease recovery and cap):** there is exactly one worker, so there is no lease, no claim-token fencing, no lease-expiry recovery and no recovery cap. The worker may ACK a doorbell message on receipt: it carries no data, and startup recovery covers a crash (OQ-46, integrator reading); a worker crash or SIGTERM gets no broker redelivery. When the worker starts, before it consumes messages, it picks up the run left `RUNNING`, the single such row (`DISPATCHED` and `CANCELLING` are no longer set, OQ-46): first it restores the dates the run left `RUNNING` from `*_previous` (or deletes the row when there was no previous status, as above; integrator reading); then the run resumes after `progress_date` (from `start_date` when it has none). A run found at worker start with `cancel_requested_at` set (the worker stopped while a cancel was pending) has its `RUNNING` dates restored and ends `CANCELLED` before processing any date (user, 2026-10-19, relayed by Lead Backend: "Keep it: a run with a cancel request found at worker restart ends CANCELLED before processing any date."; cancellation is cooperative at date boundaries, and the restore puts the run back at one). Then the worker drains the `QUEUED` requests with `take_next()` (OQ-46). **Since OQ-50:** recovery restores no dates (item 4); it resumes the run left `RUNNING` after `progress_date`, or ends it `CANCELLED` when `cancel_requested_at` is set; then the sweep runs the `QUEUED` requests (item 2).
  - **End:** `COMPLETED`, or `COMPLETED_WITH_ISSUES` when a date it wrote is `PROCESSED_WITH_ISSUES` or, on an ALL run, when one chain failed and the other reached the end of the range (with `error_code` and `error_message`, OQ-36). The run's end status and `finished_at` commit in one transaction; there is no slot to free (OQ-46). The worker then calls `take_next()` again.
  - No nested RabbitMQ message per asset or per day.
- Issue types: `MISSING_REFERENCE_PRICE` and `EXPIRED_OPEN_POSITION` (OQ-31); there is no `STALE_PREDECESSOR` and `processing.issues` has no `chain` column. A missing predecessor is an error on the run, not an issue. A `FAILED` date keeps the issues of its previous publication, with its previously published rows, until the chain commits on that date again (OQ-47 item 3).
- The predecessor rule is checked per day (above), never at enqueue: enqueueing is never refused for it (OQ-31, replacing the refusal at start of OQ-22 and OQ-30).
- There is no cancel-and-replace (OQ-30): the user cancels, or queues a new request, as separate actions.
- Cancellation of queued work is immediate: a `QUEUED` run becomes `CANCELLED` at once. Cancelling a finished run answers 409 `JOB_NOT_CANCELLABLE` (OQ-29). Cancelling a `RUNNING` run sets only `cancel_requested_at` (its status stays `RUNNING`; the screens show it as **Cancelando**, a display rule, OQ-46); a second cancel answers 409 `JOB_NOT_CANCELLABLE`, "O cancelamento deste processamento já foi solicitado." Since OQ-46 no run is `DISPATCHED`, so the `DISPATCHED` → `CANCELLING` path of OQ-29 no longer arises and `CANCELLING` is never set (integrator reading); a `CANCELLING` run, which no longer occurs, would still answer 409. A running cancellation sets `cancel_requested_at`; the worker checks it between dates: the current date commits, later dates are not touched, and the run ends `CANCELLED`; on an ALL run where one chain already failed, the run still ends `CANCELLED` and keeps the first failure's `error_code` and `error_message` (OQ-36 item 10). A cancel that arrives during the last date lets the run end `COMPLETED`, or `COMPLETED_WITH_ISSUES` when a date it wrote has issues (OQ-23, OQ-26). Overlapping requests allowed in PostgreSQL, one active global job, guaranteed by the single worker draining serially (OQ-46). Kept by OQ-50 item 6: cancellation acts between dates and nothing was left to skip; a finished run does not show "cancel requested".

## Transaction boundaries and behavior

1. **Mutation:** HTTP handler opens UoW; Ledger or Prices writes the authoritative record; one COMMIT; return response. Nothing else: no invalidation and no automatic processing job (OQ-31).
2. **Enqueue:** HTTP handler opens UoW; Processing validates requested dates; insert `requests(status=QUEUED)` and one doorbell outbox message that carries no request ID (OQ-46); COMMIT; return job ID. The doorbell only means "there is work": the queue and its order stay in PostgreSQL, and there is no message per date or per asset. RabbitMQ is kept as the worker's push wake-up (OQ-46 item 10): the request is saved first, the outbox publishes with confirms, a lost message is covered by the next message or the next worker start, and there is no polling; LISTEN/NOTIFY or polling were rejected. **Since OQ-50 item 2:** the outbox message carries the `request_id`, one per request; a lost message only delays the run until the worker's periodic sweep.
3. **Take (OQ-46, replacing the dispatcher):** there is no dispatcher process and no dispatch tick. The outbox relay publishes the doorbell with confirms. On every doorbell, and at worker start after recovery (step 6), the single worker repeats, until nothing is `QUEUED`: one transaction row-locks the oldest `QUEUED` request by `(created_at, id)`, sets it `RUNNING` with `started_at`, and commits; then it runs it (step 4). A doorbell that finds nothing `QUEUED` does nothing. `calculation_state` is not locked and `active_request_id` is not used (integrator reading); one run at a time follows from the single worker. Lock order: the take locks one `QUEUED` row; the run then locks its own row, then its dates; there is no other lock to invert. **Since OQ-50 item 2:** every run message, and the periodic sweep, take the oldest `QUEUED` request by `(created_at, id)`; the message's `request_id` is for tracing only, and FIFO is unchanged.
4. **Execute, one date per transaction (OQ-23):** the single worker (OQ-45) runs the job the take set `RUNNING` (step 3, OQ-46), with no lease and no claim token. For each date: a short transaction sets the date's chain status `RUNNING`; then the date's transaction locks the run's `requests` row and the `date_status` rows of D−1 and D in ascending date order, checks the predecessor rule, upserts D's published rows and AUM, sets D's status, the chain's `*_processed_at` and `requests.progress_date`, and commits. There is no staging and no range-wide publish. Processing controls transaction durations; calculators have no DB side effects. **Since OQ-50:** no short `RUNNING` transaction (item 4), and the writes no longer include AUM (item 1).
5. **Cancel:** a `QUEUED` job is cancelled at once (it serializes with the take on the row lock, step 3); for a `RUNNING` one the cancel flag is committed and the worker checks it between dates: the current date commits, later dates are not touched, the run ends `CANCELLED` (on an ALL run after one chain failed, keeping the first failure's error, OQ-36); a finished job answers 409 `JOB_NOT_CANCELLABLE` (OQ-29). `DISPATCHED` and `CANCELLING` are never set since OQ-46 (integrator reading).
6. **Failure and recovery:** a failing chain rolls back to its SAVEPOINT inside D's transaction, which sets that chain `FAILED` on D and stores the error on the run (integrator choice); a single-chain run ends `FAILED`; later dates are not touched and earlier ones stay published. On an ALL run, D runs in one transaction with a SAVEPOINT per chain: a technical error rolls the failing chain back to its savepoint and sets it `FAILED`, and the surviving chain's rows, AUM, `progress_date` and statuses commit in the same transaction (OQ-40); only the failing chain stops, the other continues, and the run ends `COMPLETED_WITH_ISSUES` with the first error, or `FAILED` only when both chains fail (OQ-36). A non-chain failure (outside every chain's savepoint, or an error that breaks the connection and cannot use a savepoint; integrator choice) rolls back all of D, and a short transaction sets D `FAILED` for every chain still alive in the run, with `failed_chain` NULL, and the run ends `FAILED`; a worker crash is not a failure at D (OQ-40, OQ-45). The run stores its first failure as `failed_date` and `failed_chain` (OQ-40). **A run's step that cannot be recorded (integrator reading, #115; OQ-47 item 7):** writing the run's end, or a date's non-chain failure, is retried only on a transient database error (a dropped or invalidated connection, a timeout); if that still fails, the error escapes and the worker restarts, and recovery finishes the run. Any other error (a bug, a constraint violation) would fail the same way after every restart and block the queue, so it is not retried: the run ends `FAILED` with `PROCESSING_ERROR` and "Erro técnico ao processar a data." in a fresh short transaction, its dates left `RUNNING` are restored from `*_previous` (flagged for the implementing PR, A1: since OQ-50 no date is written `RUNNING`, so nothing is restored), the dates it committed keep their statuses, and an ALL run keeps its first chain failure (`error_code`, `error_message`, `failed_date`, `failed_chain`); without one, `failed_date` and `failed_chain` stay null, since no date is left `FAILED`. After a crash or a SIGTERM, recovery happens only when the worker starts (OQ-45): the run left `RUNNING` (the single such row; OQ-46) has its `RUNNING` dates restored from `*_previous` (flagged for the implementing PR, A1: since OQ-50 no date is written `RUNNING`, so nothing is restored), then resumes after `requests.progress_date`, or, when `cancel_requested_at` is set, ends `CANCELLED` before processing any date (OQ-45); then the worker drains the `QUEUED` requests (step 3, OQ-46); there is no recovery cap (OQ-43 reversed); on an ALL run, a chain with a `FAILED` date in [`start_date`, `progress_date`] for this run stays stopped (read from `date_status`, OQ-36). A run's end frees no slot: there is none (OQ-46).
7. **Broker semantics:** RabbitMQ delivery at-least-once. The message is a doorbell with no data (OQ-46), so a duplicate or a redelivery is harmless: the take finds the next `QUEUED` request or nothing, and a lost message is recovered by any later doorbell or by a worker restart. Inbox idempotency stays in the platform, but the doorbell does not depend on it (integrator reading); `platform.inbox_messages` has a retention cleanup (OQ-47 item 2): the outbox relay's poll loop deletes the rows processed more than `INBOX_RETENTION_DAYS` ago (default 7), at most once per `INBOX_RETENTION_INTERVAL_SECONDS` (default 3600, first run at relay start); a message delivered again after that would be handled again, which the doorbell makes harmless. The worker handles one message at a time (prefetch 1) and may ACK on receipt (integrator reading): a crash is covered by recovery at worker start (step 6, OQ-45). Retries transient only; domain missing prices are `COMPLETED_WITH_ISSUES`, not retries. The relay recovers after crashes. **Since OQ-50 item 2:** the inbox, its retention cleanup (`INBOX_RETENTION_*`), the dead-letter queues, the delivery limit, the redelivery backoff and the after-ack job queue are removed; a duplicate is harmless because the request is no longer `QUEUED`, and a lost message is covered by the sweep.

**Date-status rule (OQ-23, OQ-31):** `processing.date_status` is the only source of each date's processing status; there is no staleness, no dirty markers and no revision counters. Every Portfolio read reports, for each date, the cash and positions statuses and their processing times from it (no row = not processed). A write changes no status: a processed date keeps its status and time until the user processes it again; dates after a processed range stay not processed until they are processed.

### Errors (OQ-15)

Every error response is RFC 9457 `application/problem+json`:

```json
{"type": "about:blank", "title": "…", "status": 422, "detail": "…",
 "errors": [{"code": "FUTURE_DATE", "message": "A data não pode ser posterior a hoje.", "field": "entry_date"}]}
```

`message` is pt-BR; `code` is English. Catalogue (extended additively by the integrator):

| Code | Status | Meaning |
|---|---|---|
| `VALIDATION_ERROR` | 422 | Malformed or out-of-bounds input (schema CHECK rules, too many decimals) |
| `FUTURE_DATE` | 422 | An entry or price written with a date after today (São Paulo; not `GET /reference-prices`, OQ-42), a processing range (request, preview) ending after today (OQ-29), or a Portfolio read (`summary`/`positions` `date`, `pnl` `end_date`) after today (OQ-35) |
| `CONTRACT_MATURED` | 422 | A trade or reference price dated after the instrument's maturity |
| `NOT_FOUND` | 404 | The resource in the URL path does not exist. An unknown id in the request body (e.g. `product_id`, `asset_class_id`) is a 422 `VALIDATION_ERROR` on that field (OQ-33). Exception: the `ids` of `POST /ledger/entries/deletions` are the resources being deleted, so an unknown or already-deleted id answers 404 and nothing is deleted (OQ-32) |
| `INVALID_RANGE` | 422 | A processing or query range with start after end, or a start with no predecessor day (0001-01-01) |
| `JOB_NOT_CANCELLABLE` | 409 | Cancel requested for a job that is already finished, or a second cancel of a `RUNNING` job (OQ-29; `CANCELLING` is never set since OQ-46) |

Run error codes are not HTTP statuses: they are stored on the run as `error_code` with a pt-BR `error_message`, read through the run's DTO and shown in Processamentos (OQ-36 item 6):
- `CASH_PREDECESSOR_MISSING` / `POSITIONS_PREDECESSOR_MISSING`: "Dia anterior não processado" (predecessor rule above, OQ-31).
- `PROCESSING_ERROR`: "Erro técnico ao processar a data." — a technical failure on D, of a chain or of no chain (OQ-44).
- `RECOVERY_EXHAUSTED`: retired by OQ-45 (there is no recovery cap); never written.

## DI composition

`modules/<name>/public.py` exposes stable read/service contracts and DTOs; `modules/<name>/dependencies.py` creates module-local implementations; `composition/dependencies.py` wires cross-module collaborators and UoW; `composition/routers.py` registers routes; `composition/consumers.py` registers handlers; workers use plain factories, not FastAPI `Depends`. No one-class-per-command framework; cohesive application services.
