## Should trades and cash movements be one "ledger entry"?

**Context.** Maravi DI1 is a backoffice for one portfolio of DI1 futures. The ledger records two kinds of user input:
- **trades:** compra or venda of a contract, with a quantity and an execution PU or rate;
- **cash movements:** aporte or retirada, with an amount.

A daily processing job reads them to compute cash, positions and P&L. Cash and positions are processed as two separate chains (OQ-21): a trade changes both, and a cash movement changes only cash.

### How it works today

Two tables (`docs/schema.sql`):

| `ledger.trades` | `ledger.cash_movements` |
|---|---|
| `id, asset_id, trade_date, trade_time, seq (identity), signed_quantity, execution_pu, execution_rate, input_kind` | `id, movement_date, movement_type (DEPOSIT/WITHDRAWAL), amount NUMERIC(20,2) > 0, description` |
| `created_at, deleted_at, delete_reason` | `created_at, deleted_at, delete_reason` |
| ordered by `(trade_date, trade_time, seq)` | no time (GAP-I-1 confirmed "date only") |

Service and reader (`docs/interfaces.md`):
- **Writes:** `create_trade`, `delete_trade(id, reason)`, `create_cash_movement`, `delete_cash_movement(id, reason)`.
- **Reads:** `get_trades(range)`, `get_cash_movements(range)`.

HTTP:
- `POST/GET /trades`, `DELETE /trades/{id}`;
- `POST/GET /cash-movements`, `DELETE /cash-movements/{id}`.

The frontend added two proposals:
- `GET /ledger/entries` (P18), which merges both into one list on the server;
- `POST /ledger/deletions {trade_ids, cash_movement_ids}` for an atomic multi-delete (spec §6.1).

### The problem the user raised

On the Lançamentos screen both kinds are one list. A single "Novo lançamento" modal creates any of the four types, and a selection can mix both kinds when deleting. Even so, the API makes the client know which table each row came from: it needs separate endpoints, a delete body with two id lists, two error-field vocabularies, and cash rows with no time. The user's position: *"Their separation should be their type only."*

### What the user decided (2026-10-18)

1. **One entity.** A ledger entry has `type: TRADE | CASH`.
2. **Time and order:** every entry has `date`, `time` and a shared `seq`. Ordering is `(date, time, seq)` across both types. This reverses GAP-I-1, since cash now has a time.
3. **Cash amount:** it is signed in `cash_amount`, positive for an aporte and negative for a retirada, instead of `movement_type` plus a positive `amount`. A trade keeps `signed_quantity`, and its `cash_amount = −qty × PU` comes from the backend.
4. **API:** three calls replace all the endpoints above.
   - `GET /ledger/entries?start_date&end_date&search&order`
   - `POST /ledger/entries {type, date, time, …}`
   - `DELETE /ledger/entries {ids: [...]}`: one transaction, all or nothing, with **no reason**.
5. **Scope:** the API **and the database**, so the two tables become one.

### Questions for review

1. **Table design.** A single table means trade-only columns (`asset_id`, `signed_quantity`, `execution_pu`, `execution_rate`, `input_kind`) are nullable for cash. The usual way to keep integrity is CHECK constraints per type. The alternative is a parent `ledger.entries` table, holding id, type, date, time, seq, cash_amount and soft delete, plus a `ledger.trade_details` child table. Which is cleaner and easier to defend?
3. **A stored `cash_amount` on trades.** Today a trade's cash effect is derived (`−qty × PU`). Storing it duplicates data and risks inconsistency. Leaving it out means the API computes it on read for trades only. Which?
3. **Ordering semantics.** Does an intraday time on cash change any accounting? Spec §7: `cash[D] = cash[D−1] − Σ(qty × PU) + deposits − withdrawals` is daily, so order within a day shouldn't matter for cash. Trades must still be applied in `(date, time, seq)` order for average PU and zero-crossing. Does a shared `seq` across types break or complicate anything?
4. **Dropping the delete reason.** The schema has `delete_reason`, and `interfaces.md` has `delete_trade(id, reason)`. The spec says history is immutable, with soft delete and an audit trail. Is the audit still satisfied by `deleted_at` (plus who deleted it, if tracked) without a reason?
5. **A DELETE with a body.** HTTP allows it, but some proxies and clients handle it badly. Should it be `DELETE /ledger/entries` with a body, `DELETE /ledger/entries?ids=a,b`, or `POST /ledger/entries/deletions`?
6. **Effect on other modules.**
   - Portfolio (lane E) reads `LedgerReader.get_trades`/`get_cash_movements` through `public.py`. Should the reader become `get_entries` filtered by type, or keep two typed reads over one table?
   - Processing marks dirty markers per write (a trade affects the cash and positions chains, cash only the cash chain), and that has to follow `type`.
7. **Timing.** Delivery is Monday 19/10. The backend modules are being built now, and the migration and contracts belong to the integrator. Is this worth doing now, or should the API be unified now and the tables merged later?

### Already done on the frontend (lane I)

- **Done:** the frontend contract (`frontend/src/api/contract/ledger.ts`) and the endpoint client are rewritten to the shape above.
- **In progress:** the mocks, the unified "Novo lançamento" form and the tests. Nothing is committed.

- take the `type=TRADE` entries and map them onto `Trade` (rename `date`/`time` to `trade_date`/`trade_time`);
