### 👤 User · 2026-10-18 17:58

but why is trade in portfolio. This should be in the ledger. The portfolio module is only for us to have everything related to the portfolio screen. Can you explain this to me?


#### 🤖 Claude · 2026-10-18 17:58


Ledger does own trades. Portfolio doesn't create, store or change them. But the docs give Portfolio more than the screen:

- **Spec §2:** Portfolio's job is to "reconstruir posições e estado de caixa por dia; manter posições e métricas calculadas; servir consultas consolidadas". The screen is the third part. The first part is the accounting engine I'm building.
- **interfaces.md "Portfolio" and plan §4.E** put `PortfolioAccounting.calculate_day(previous_state, trades, …)` in Portfolio, and say it runs "using yesterday's state and day's sorted events".

To turn trades into positions, the engine has to read each trade's asset, quantity, PU, rate and its `(date, time, seq)` order. That's the only reason a trade shape shows up in Portfolio.

**Why I didn't just import Ledger's type.** The architecture tests (backend/CLAUDE.md, `domain-purity`) let `domain/` import only the standard library, `di1.shared` and its own domain. It can't import `ledger.public`. Ledger's public DTOs don't exist yet either (W0.3b). So I declared a local copy. That is a second `Trade` entity, and your objection is fair.

**Ways to fix it:**
1. **A Protocol, not a class (my recommendation).** Portfolio's domain declares only the fields it reads, as a `typing.Protocol`, something like `TradeInput` with `asset_id`, `trade_date`, `trade_time`, `seq`, `signed_quantity`, `execution_pu`, `execution_rate`. It has no data and no constructor. Ledger's public `Trade` DTO already has those fields, so it gets passed straight in, with no copy and no mapping. Ledger stays the only owner of the trade, and the architecture rule holds. In tests, a tiny fixture class has those fields.
2. **Put the trade DTO in `di1.shared`.** Both modules use the same type. It's integrator-owned and couples Ledger's contract to a shared package.
3. **Let the domain import `ledger.public`.** This changes the architecture rule, needs the integrator, and makes the Portfolio domain depend on Ledger.
4. **Move the accounting engine out of Portfolio.** This makes Portfolio read-only, as you describe. It changes spec §2, interfaces.md and the plan's lanes, and needs a recorded decision. The engine would still have to sit somewhere that reads trades, so the same question just moves there.

Unless you want to redefine the Portfolio module (option 4), I'd take option 1.

- ✅ **Wrap-up**: Nothing is committed. I explained that the spec puts the accounting engine in Portfolio, and that the domain can't import Ledger, which is why a local Trade copy exists. The recommendation is to replace it with a Protocol so Ledger stays the only owner.

Ledger will have its trade DTO, and Portfolio has my `Trade`. That's three copies of one concept before Wave 2 has even started, and they'll drift: different names, different validation, each with its own mapping code.

**Why shared fits here:**
- **Several modules read the same trade facts.** Portfolio needs quantity, PU, rate and order to compute positions and cash. PnL needs quantity and PU for `trades_pnl`. Processing passes them between the two. backend/CLAUDE.md allows `shared/` for "only DTOs that are genuinely shared", and this is the clearest case in the project.
- **Little churn risk.** Trades are immutable and the schema is fixed, so a shared type won't keep changing under its users.
- **The architecture stays as it is.** Domain code may already import `di1.shared`, so no rule has to change.
- **It's easy to explain in the interview.** Ledger owns the facts. `shared` holds the one value type that describes a trade's economics. The calculators read that type and don't own it.

**What should stay out of shared:**
- Ledger's record metadata: `id`, `created_at`, `deleted_at`, `delete_reason`, and `input_kind` too. Those stay in Ledger's public DTO, which can wrap the shared value or expose it.
- Behaviour. Order and validation rules belong to whoever applies them, apart from trivial invariants like quantity ≠ 0.
- Anything only one module uses, so shared doesn't turn into a dumping ground.

**Compared with the Protocol I suggested:** the Protocol works, but each consumer would declare its own field list. That removes the duplicated ownership but keeps duplicated shapes, and it adds structural typing for a reader to follow. With three consumers and a delivery tomorrow, one concrete frozen dataclass is simpler.

**Cost:** `shared/` is integrator-owned, so this needs a contract-change request. Lane F has to swap `PnLTrade` for the shared type, so it has to be coordinated now, before F and E open their PRs.

What I'd propose to the integrator: a `di1.shared.trades.Trade` frozen dataclass with `asset_id`, `trade_date`, `trade_time`, `seq`, `signed_quantity`, `execution_pu` and `execution_rate`, plus an `order_key`. Ledger's public DTO exposes it, and Portfolio and PnL import it. Until it lands on main, I can keep my type in the same shape, so the switch is a one-line import change.
