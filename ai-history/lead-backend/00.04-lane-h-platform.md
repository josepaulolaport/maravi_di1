#### 🤖 Claude · 2026-10-19 11:15


The lease is how the system notices that the worker running a processing job has died. The worker holds the job only for a limited time and keeps renewing that hold while it works; if the renewals stop, the system takes the job back.

How it works:

1. **Claim.** When the worker picks up a dispatched job, it records in PostgreSQL (`processing.requests`) a fresh claim token and an expiry time: now + 60 s. That pair is the lease.
2. **Renew.** After each calendar day it processes, the worker pushes the expiry another 60 s ahead (OQ-5: "60 s, renewed after each processed day").
3. **Fence.** Before every write, the worker checks that its token still matches and its lease hasn't expired. If either check fails, the worker has lost the job and writes nothing.
4. **Recover.** If the worker crashes, hangs or loses its connection, renewals stop and the lease expires. The dispatcher sees a RUNNING job with an expired lease and dispatches it again. The new worker claims it with a new token and continues after the last committed day (`progress_date`). If the old worker comes back, the fence turns its writes into no-ops, so two workers never write the same run.

This is also why the recovery cap matters: each re-dispatch after an expired lease counts as one recovery attempt. After 3 (`PROCESSING_MAX_RECOVERY_ATTEMPTS`), the run ends FAILED instead of being retried forever.

On the length: if it's too short, a slow but healthy day can lose its lease and be re-run needlessly. If it's too long, a crashed run waits longer before it's recovered. OQ-5 set 60 s; PR #83 lets you change it with `PROCESSING_LEASE_SECONDS`.
