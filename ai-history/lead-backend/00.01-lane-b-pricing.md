### 👤 User · 2026-10-18 17:34

what is the best practice for static variables?


#### 🤖 Claude · 2026-10-18 17:34


Short version: put each constant in the module that owns its meaning, and move it to `di1/shared` only when two or more modules really need it. A constant is for a fixed fact; a value that varies belongs in configuration or the database.

**General practice in Python:**
1. **Naming.** Use module-level `UPPER_SNAKE_CASE`, with a docstring saying what it is and where the rule comes from. You can add `Final` from `typing` so mypy rejects any reassignment.
2. **Ownership.** Keep a constant next to the code that defines what it means. Avoid a catch-all `constants.py`: it pulls unrelated ideas together, and every module ends up importing it.
3. **Sharing.** Share only what several modules actually use. Otherwise, other modules get the value through the owner's public API (here, `public.py`).
4. **Closed sets.** When the values form a fixed list, make it an `Enum`/`StrEnum` rather than loose strings. `InputKind` already does this.
5. **Immutability.** Use immutable values only: `Decimal`, `str`, `tuple`, `frozenset`, or `MappingProxyType` for a read-only dict. Never a bare `dict` or `list`.
6. **Constant, config or data:**
   - fixed by the spec (365 days, 34 digits, 10/12 dp): a constant in code;
   - changes per deployment (limits, URLs): settings (`platform/config`);
   - business data (face value, multiplier): the database (`asset.futures`), never copied into code.

**Applied to this branch:**
- **Keep in shared:** `calendar_days` and `DAYS_PER_YEAR`. Portfolio's daily loop and the maturity checks in Ledger and Prices will use them, and they sit beside `PU_PLACES`/`RATE_PLACES` in `shared/decimals.py`.
- **Move back to pricing:** `CHALLENGE_DC_365` and its version. Only Pricing produces them, and other modules see them through `PricingResult.methodology` and `version`. The methodology class itself is the right owner. Having them in shared is the "dump it in shared" smell.
- **Optional `Final`:** I could add `Final` to the new constants. The existing `shared/decimals.py` doesn't use it, so I'd add it to both files or to neither, to stay consistent.

My recommendation: move the methodology identity back onto `Dc365Methodology`, delete `shared/pricing_conventions.py` and its test, and keep `shared/calendar.py`. I'd leave `Final` out to match the existing pattern. Should I make that change?
