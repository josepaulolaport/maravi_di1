1. **H1, a stuck queue:** `PortfolioRangeProcessor.run()` (backend/src/di1/modules/processing/application/services/run_processor.py ~239) swallows every exception, so a run whose end/fail write itself fails (DB blip in _fail_day/_complete) stays RUNNING. take_next (~173) then returns None forever because lock_active_runs finds it. Fix: retry the end-of-run/fail-date write with a short bounded backoff; if it still fails, let the error escape so the worker process exits non-zero, Compose restarts it, and startup recovery (OQ-45) resumes the run. Test both: a transient failure that the retry absorbs, and a persistent one that ends the process / propagates (and that recovery then finishes the run).
2. **Healthchecks:** add Compose healthchecks for `worker` and `outbox-relay` (neither has one); a cheap, honest check (e.g. a heartbeat file the loop touches, or a tiny probe command). Keep `restart:` policies sensible.
3. **H4, locks held while publishing:** platform/messaging/outbox_relay.py (~86-108) publishes inside the FOR UPDATE SKIP LOCKED transaction, holding locks up to batch_size × confirm timeout when the broker is down. Fix: claim rows in a short transaction, publish outside it, mark published in a second short transaction (a duplicate publish is already harmless: inbox idempotency); at minimum stop the batch at the first connection failure. Tests on PostgreSQL + RabbitMQ.
4. **User decision (M9): keep the inbox, add retention.** platform.inbox_messages grows forever (one row per doorbell). I sent the link to the merger and to Lead Backend; nothing is merged.

- **H1, stuck queue:** the writes that end a run or mark a date failed are now retried after 0.5 s, 2 s and 5 s. If they still fail, the error is no longer swallowed: the worker exits 1, Compose restarts it, and recovery at startup finishes the run. Tests cover a failure that the retry absorbs, and a persistent one where the run stays RUNNING, the next request stays QUEUED, and a restart completes both.
- **H4, locks held while publishing:** the relay reads its rows in one short transaction, publishes with no transaction open, and records the results in a second one. When the broker is unreachable (a timeout or a closed channel), the batch stops at the first row and that row is not paused, so the next poll retries it. The new tests failed against the old relay and pass now.
- **M9, inbox retention:** inbox rows older than 7 days are deleted, checked once an hour (`INBOX_RETENTION_DAYS`, `INBOX_RETENTION_INTERVAL_SECONDS`). The relay's poll loop runs it, because the worker has no periodic loop. No schema change. As you asked, `docs/interfaces.md` TB7 and the inbox row in `docs/schema.md` now describe it in the present tense.
- **Healthchecks:** each process touches a heartbeat file, and `python -m di1.workers.healthcheck` passes while that file is under 30 s old. It opens no database or broker connection. `restart: unless-stopped` stays. Docker does not restart an unhealthy container, so the restart comes from the process exiting.

Three things for review:
- A database blip while the worker is picking the next request now restarts the worker too; before, it was only logged. The request stays QUEUED and is picked up after the restart.
- `workers/healthcheck.py` is a new file that plan §1 doesn't list. The architecture tests pass, and it can move under `platform/observability/` if you prefer.
- Two things are not verified: Compose restarting a real container after a real database failure (only the code path is tested), and a broker that hangs without closing. Only the closed-channel case runs against real RabbitMQ.
