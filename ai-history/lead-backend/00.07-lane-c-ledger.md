Processing needs it to decide whether day D can be computed from nothing. It isn't something Ledger needs for itself.

**The rule it serves** (lane X's PR #54, `interfaces.md` "Predecessor rule, per day", OQ-31 and OQ-37):
- Before Processing computes day D for a chain, the day before (D−1) must already be processed for that chain. That is the starting point D builds on.
- The one exception is the chain's **zero state**: nothing has happened yet, so starting from zero is correct.
  - **Positions** are in the zero state when no trade is dated on or before D−1.
  - **Cash** is in the zero state when no entry of either type (trade or deposit/withdrawal) is dated on or before D−1. Trades move cash too.

**What goes wrong without it.** Say you trade on 10/14 and then ask to process only 10/20. Processing finds no processed result for 10/19. It has to tell two cases apart:
- Nothing happened before 10/20: start from zero cash and no positions. Correct.
- Trades happened but were never processed: starting from zero would publish wrong numbers. The run has to fail on that date instead.

Only Ledger knows whether entries exist before a date. Processing may not read Ledger's table directly, so it asks through Ledger's public contract:
- `has_entries_on_or_before(D−1, entry_type=TRADE)` answers for positions.
- `has_entries_on_or_before(D−1)` answers for cash.

It's one cheap `EXISTS` query.

The Processamentos preview uses the same check to warn, before you enqueue, that a range would fail on its first day.

Could Processing manage without it? It could call `get_trades` and `get_cash_movements` from the first possible date up to D−1 and check whether the lists are empty. That loads every entry just to answer yes or no, so lane X added the dedicated method.
